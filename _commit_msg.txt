fix(security): replace the forgeable demo token with signed JWT

RadioStack's API was fully open: SecurityConfig declared
anyRequest().permitAll() while exposing POST, PUT, PATCH and DELETE on
programmes, presenters, broadcasts, comments and chat.

Underneath it, the token was the string "Bearer-demo-" followed by the
user id, with no signature, no secret and no expiry. Sending
"Authorization: Bearer-demo-1" impersonated user 1. The surrounding code
looked like real authentication -- AuthController, /login, BCrypt password
comparison, a /me returning 401 -- which made the placeholder easy to
mistake for a working mechanism.

HTTP:
- JwtService signs with HMAC-SHA256. The key comes from
  RADIOSTACK_JWT_SECRET and has no default on purpose: a default in the
  repository would be a public key anyone could mint tokens with. Keys
  shorter than 256 bits are rejected at startup.
- JwtAuthenticationFilter populates the security context but never
  rejects a request, so access rules stay in one place: SecurityConfig.
- SecurityConfig now permits login and GET, and requires a token for
  everything that changes data. Unauthenticated requests get 401 instead
  of 403 via an authenticationEntryPoint.
- /me re-reads the database to confirm the account is still active. JWTs
  cannot be revoked, so a deactivated user's token stays cryptographically
  valid until it expires.

WebSocket chat:
- The servlet filter cannot cover STOMP: the connection is established by
  a single handshake that carries no Authorization header, and later
  frames travel outside the request/response cycle. Authentication now
  happens in the STOMP CONNECT frame, the first one that accepts custom
  headers, via StompAuthChannelInterceptor.
- Same policy as HTTP, deliberately: SUBSCRIBE to /topic is public, SEND
  to /app requires a valid token. A CONNECT without a token is accepted as
  anonymous; one with an invalid token is rejected rather than downgraded.
- The chat alias came from the message payload, so anyone could sign as
  someone else. It now comes from the verified token.
- StompClient sends the token in CONNECT and handles ERROR frames, which
  it previously discarded silently, leaving rejected sends unexplained.

BREAKING CHANGE: the desktop client sent "Authorization: <token>" without
the Bearer scheme, because the prefix was baked into the demo token
string. ApiClient now adds it. The admin module must be rebuilt. The
"alias" field in chat.fxml no longer has any effect.

Also in HashTools, KeyPairManagerRSA.generarClaves used neither of its two
parameters: it never called kpg.initialize(...), so Java produced a
2048-bit key with the default random source and ignored both. Both dead
parameters were traps for anyone wiring them up:

- The only caller passed 256, copied from the AES key generation. For RSA
  that is a category error; initialize(256) throws.
- Seeding SecureRandom from the password would have made key generation
  deterministic, letting anyone who knows the password reproduce the
  private key. PasswordValidator allows 8 to 20 characters.

Now calls initialize(2048) with the system random source and rejects
smaller sizes. Observable behaviour is unchanged; existing key files
remain valid.

Also derive the FTP passive-mode announcement from HOST instead of a
hardcoded literal, and drop the unused ip_anuncio variable.
