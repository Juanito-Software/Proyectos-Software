fix(security): validate YouTube URLs by host; migrate Angular tests to Vitest

YoutubeToMp4 decided whether a string was a YouTube link with
`"youtube.com" in modo`. Substring matching on a whole URL is not a host
check: https://youtube.com.example.net/x and https://evil.net/?ref=youtube.com
both satisfy it, because the URL contains path, query and fragment that the
author of the link controls.

That particular line was only a convenience heuristic, but the real gap was
elsewhere and CodeQL did not flag it: neither the interactive mode nor the
CSV mode checked the destination at all. The interactive path only required
an http:// or https:// prefix; the CSV path checked nothing.

Added es_url_de_youtube(), which parses with urlparse and compares the
hostname against an allow-list. Subdomain matching uses a leading dot
(".youtube.com") so that "mi-youtube.com" does not pass, and the scheme is
restricted to http/https, which rules out file:// and javascript:. The
check lives in descargar_video_mp4(), the single point both modes go
through, rather than being repeated at each entry point.

Verified against 14 cases, including the four the previous filter wrongly
accepted. All pass. This closes the last of the nine CodeQL families.

Separately, migrate the Angular TaskHub test setup from Karma to Vitest.
The vulnerable brace-expansion chain entered through Karma, so the branch
was removed rather than chased. Angular 21 ships Vitest as the default
runner.

- Builder changes from @angular/build:karma to @angular/build:unit-test.
- Build options (polyfills, assets, styles) move out of the test target,
  which the new builder does not support; they already exist on the build
  target. zone.js/testing is not needed: the single spec uses neither
  fakeAsync nor waitForAsync.
- Added a "testing" build configuration disabling ssr and outputMode
  server. Without it the builder would use "development", which drags the
  SSR server into the test build.
- tsconfig.spec.json types go from jasmine to vitest/globals.
- The spec file is unchanged; its matchers are already Vitest-compatible.

Both tests pass and npm vulnerabilities in that project drop from 12 to 3,
removing all six high-severity ones. The dependency tree goes from 668 to
519 packages.

Uninstalling Karma was not enough on its own: audit still reported
brace-expansion -> minimatch -> glob -> karma -> @angular/build. Angular
declares both runners as OPTIONAL peer dependencies, which npm does not
install, so that Karma was a leftover surviving in package-lock.json from
when it was a direct dependency. npm uninstall drops the declaration but
does not prune the tree; the lockfile and node_modules had to be
regenerated.

The remaining three moderate advisories
(@angular/cli -> @modelcontextprotocol/sdk -> @hono/node-server) are left
open on purpose: the only fix npm offers is downgrading @angular/cli. Same
policy as the other upstream-blocked alerts -- not dismissed, left open to
close by itself when Angular updates.

npm audit fix --force was never run. It proposed @angular/build@19.1.9 and
@angular/cli@21.0.4, undoing the Angular 21 upgrade. Downgrading is not
fixing.

Also bump @types/node from ^18.18.0 to ^22. Vitest 4 requires 20, 22 or
24+, and the project was building against types for a Node version it does
not run -- the installed runtime is 22.16.0, and Node 18 is end-of-life.
Resolved by upgrading rather than with --force or --legacy-peer-deps: the
peer conflict was real.

NOTE: Angular documents migrating an existing project to Vitest as
experimental.
