Regla de oro: una respuesta solo está verificada si la has ejecutado o si puedes justificarla con la especificación del lenguaje. Esto también aplica a lo que te diga cualquier asistente de IA, incluido yo.

Parte 1 — Fundamentos de programación con Java
Esta parte resume lo que ya has estudiado: tipos, referencias, operadores, control de flujo, métodos, arrays, POO básica y excepciones. Las correcciones a errores del itinerario están marcadas como Corrección.
1.0 Cimientos: qué es programar en Java, desde cero
Esta sección no da nada por sabido. Si ya la dominas, salta a 1.1; si alguna palabra de las secciones siguientes te suena a chino, vuelve aquí.
Qué es un programa
Un ordenador solo sabe hacer operaciones muy simples (sumar, comparar, copiar datos de un sitio a otro), pero muy rápido. Un programa es una lista de instrucciones que le dice exactamente qué operaciones hacer y en qué orden. Es como una receta de cocina escrita para alguien que lo hace todo al pie de la letra y no improvisa nada: si la receta tiene un error, el resultado será incorrecto aunque el cocinero sea perfecto.
Un lenguaje de programación es el idioma en el que escribimos esas instrucciones. El procesador no entiende Java directamente; entiende código máquina (ceros y unos). Por eso hace falta un paso de traducción.
Cómo se ejecuta un programa Java
Java traduce en dos pasos:
    1. Escribes el código fuente en un fichero Hola.java (texto normal).
    2. El compilador javac lo revisa y lo traduce a bytecode, un fichero Hola.class. Si hay errores de escritura o de tipos, se detiene aquí: es un error de compilación.
    3. La JVM (Java Virtual Machine, la “máquina virtual”) lee el bytecode y lo ejecuta en tu sistema operativo. Los errores que aparecen ahora, con el programa ya en marcha, son errores de ejecución (excepciones).
Gracias a la JVM, el mismo .class funciona en Windows, Linux o macOS: “escríbelo una vez, ejecútalo en cualquier parte”.

Tu primer programa, línea a línea
public class Hola {                              // 1. una clase llamada Hola
    public static void main(String[] args) {     // 2. el punto de entrada
        System.out.println("Hola, Juan");       // 3. una instrucción
    }                                            // 4. fin de main
}                                                // 5. fin de la clase
    1. En Java todo el código vive dentro de una clase. El fichero debe llamarse igual que la clase pública: Hola.java.
    2. main es el método por el que la JVM empieza a ejecutar. Su firma siempre es esta. public = accesible desde fuera; static = se puede llamar sin crear un objeto; void = no devuelve nada; String[] args = los argumentos que se le pasen desde la terminal.
    3. System.out.println(...) escribe un texto en la consola y salta de línea. System.out.print(...) no salta de línea.
    4. y 5. Las llaves { } delimitan bloques: dónde empieza y acaba la clase, el método, un if…
Para ejecutarlo desde una terminal:
javac Hola.java      # compila: genera Hola.class
java Hola            # ejecuta: imprime "Hola, Juan"
Desde Java 11 puedes hacer java Hola.java directamente con programas de un solo fichero. Y para probar líneas sueltas sin crear clases existe jshell, una consola interactiva: escribes int x = 5 * 3; y te responde x ==> 15. Úsala para comprobar cada ejemplo de estos apuntes.
Reglas básicas de escritura (sintaxis)
    • Cada instrucción termina en punto y coma ;.
    • Java distingue mayúsculas y minúsculas: edad y Edad son variables distintas; System con minúscula no compila.
    • Comentarios: // hasta el final de la línea y /* varias líneas */. El compilador los ignora; sirven para las personas. /** ... */ es Javadoc, documentación que se puede generar automáticamente.
    • Los espacios y saltos de línea dan igual para el compilador, pero la indentación (sangría) hace el código legible: cada bloque interior, cuatro espacios más.
    • Convenciones de nombres: clases en PascalCase (CuentaBancaria), variables y métodos en camelCase (saldoActual, calcularTotal()), constantes en MAYUSCULAS_CON_GUIONES (MAX_INTENTOS), paquetes en minúsculas (com.juan.tareas). No son obligatorias, pero todo el mundo las sigue y en una entrevista se nota.
Variables: cajas con nombre y tipo
Una variable es un espacio de memoria con un nombre donde guardas un dato para usarlo después. En Java cada caja tiene una etiqueta de tipo que dice qué puede contener; no puedes meter texto en una caja de números.
int edad = 30;            // tipo int (entero), nombre edad, valor 30
double precio = 9.99;     // número con decimales
boolean activo = true;    // verdadero o falso
char inicial = 'J';       // un carácter, comillas simples
String nombre = "Juan";   // texto, comillas dobles (String es una clase, no un primitivo)

edad = edad + 1;          // se lee: "edad pasa a valer lo que valía más 1" → 31
El = no significa “igual” como en matemáticas: significa asignar (“guarda a la derecha en la caja de la izquierda”). Para comparar se usa ==.
Operaciones y decisiones, en pequeño
int a = 7, b = 2;
System.out.println(a + b);   // 9
System.out.println(a / b);   // 3   ← división entera: entre enteros se pierde el decimal
System.out.println(a % b);   // 1   ← resto de la división (módulo)
System.out.println(a / 2.0); // 3.5 ← si uno es decimal, el resultado es decimal

if (a > b) {
    System.out.println("a es mayor");
} else {
    System.out.println("b es mayor o igual");
}

for (int i = 1; i <= 3; i++) {     // empieza en 1; repite mientras i <= 3; suma 1 cada vuelta
    System.out.println("Vuelta " + i);
}
i++ es una forma corta de i = i + 1. El + entre un texto y un número concatena (une) en lugar de sumar: "Vuelta " + 1 da "Vuelta 1".
Leer datos del teclado
import java.util.Scanner;                 // traer una clase de la biblioteca estándar

public class Saludo {
    public static void main(String[] args) {
        Scanner teclado = new Scanner(System.in);
        System.out.print("¿Cómo te llamas? ");
        String nombre = teclado.nextLine();
        System.out.print("¿Cuántos años tienes? ");
        int edad = teclado.nextInt();
        System.out.println("Hola " + nombre + ", el año que viene tendrás " + (edad + 1));
    }
}
Fíjate en los paréntesis de (edad + 1): sin ellos, Java concatenaría primero el texto con edad y luego con 1, y escribiría “tendrás 301”.
Métodos: recetas con nombre
Un método agrupa instrucciones bajo un nombre para reutilizarlas. Recibe datos (parámetros) y puede devolver un resultado (return).
static int doble(int numero) {   // recibe un int, devuelve un int
    return numero * 2;
}
// En main: int r = doble(21);  → r vale 42
Clases y objetos: el plano y la casa
Una clase es un plano o molde: describe qué datos (atributos) y qué acciones (métodos) tendrá algo. Un objeto es una cosa concreta construida con ese plano. Con el plano de “Coche” puedes fabricar muchos coches, cada uno con su color y su matrícula.
class Coche {
    String matricula;      // atributos: los datos de cada coche
    int kilometros;

    void conducir(int km) {   // método: lo que un coche sabe hacer
        kilometros += km;
    }
}

Coche miCoche = new Coche();   // new construye un objeto a partir del plano
miCoche.matricula = "1234ABC";
miCoche.conducir(100);         // el punto (.) accede a lo que hay dentro del objeto
System.out.println(miCoche.kilometros);   // 100
La variable miCoche no es el coche: es una referencia, una especie de mando a distancia que apunta al coche guardado en memoria. Esta idea es la base de toda la sección 1.2 y la que más se pregunta en entrevistas.
Paquetes e imports
Las clases se organizan en paquetes, como carpetas: java.util contiene Scanner, ArrayList, HashMap… Para usar una clase de otro paquete se escribe import java.util.ArrayList; al principio del fichero. Las de java.lang (String, System, Math, Integer) se importan solas.
Cómo leer un error
Los errores asustan al principio, pero siempre dicen qué y dónde:
Hola.java:3: error: ';' expected
        System.out.println("Hola")
                                  ^
Fichero Hola.java, línea 3, falta un punto y coma donde marca la flecha. Un error de ejecución se ve así:
Exception in thread "main" java.lang.ArithmeticException: / by zero
    at Main.main(Main.java:5)
Tipo de excepción (ArithmeticException), mensaje (/ by zero) y la línea donde ocurrió (Main.java:5). Esa lista de “at …” es la pila de llamadas (stack trace): se lee de arriba abajo, y la primera línea que sea de tu código suele ser el sitio del fallo.
Herramientas para trabajar
    • Un IDE (entorno de desarrollo) como IntelliJ IDEA o VS Code con la extensión de Java: colorea el código, marca errores mientras escribes, autocompleta y permite depurar.
    • Depurar (debug) es ejecutar el programa paso a paso: pones un punto de ruptura (breakpoint) en una línea, el programa se detiene ahí y puedes ver el valor de cada variable. Es la forma más rápida de entender por qué el código no hace lo que esperas.
    • En entrevistas a veces no hay IDE: practica también escribiendo código en papel o en un editor simple, sin autocompletado.

Reglas que caen en tests:
    • Una variable local debe inicializarse antes de leerse; si no, error de compilación. Los campos reciben valores por defecto (0, false, null).

1.2 Valores, referencias e identidad
Una variable primitiva guarda el valor. Una variable de referencia guarda una referencia a un objeto, o null.
int a = 10;
int b = a;   // copia el valor
b = 20;      // a sigue valiendo 10

Persona p1 = new Persona();
Persona p2 = p1;          // copia la REFERENCIA: un solo objeto
p2.nombre = "Luis";      // p1.nombre también es "Luis" (aliasing)
p2 = new Persona();       // reasigna p2; p1 no cambia
Distingue siempre tres cosas: la variable, la referencia que contiene y el objeto al que apunta.
    • Mutar: cambiar el estado del objeto (p2.nombre = ...). Lo ven todas las referencias.
    • Reasignar: hacer que una variable apunte a otro objeto (p2 = new ...). Solo afecta a esa variable.
    • final impide reasignar la variable, no hace inmutable el objeto.
    • String es inmutable: texto = texto + "x" crea otra cadena y reasigna la variable.
    • null significa “sin objeto”. Acceder a un miembro de una referencia null lanza NullPointerException en ejecución.

1.3 Paso de argumentos: siempre por valor
Java pasa todos los argumentos por valor. Si el argumento es una referencia, se copia la referencia.
static void cambiar(Caja caja) {
    caja.valor = 50;     // muta el objeto compartido: el llamador lo ve
    caja = new Caja();   // reasigna la copia local
    caja.valor = 100;    // afecta solo al objeto nuevo

// original.valor empieza en 10 → tras cambiar(original) vale 50
Respuesta de entrevista: “Java es siempre paso por valor. Con objetos se copia el valor de la referencia, así que el método puede mutar el objeto, pero reasignar el parámetro no cambia la variable del llamador.”

1.5 Control de flujo
    • En if / else if / else se ejecuta como máximo una rama: la primera cuya condición es true.
    • switch moderno (Java 14+) con flechas no tiene fall-through: case 1 -> "uno";. El clásico con : sí cae al siguiente case sin break.

1.6 Métodos
    • Parámetros se declaran en la firma; argumentos se pasan en la llamada.
    • void no devuelve valor, pero admite return; para salir antes.
    • Un método con tipo de retorno debe devolver un valor compatible en toda ruta que termine normalmente.
    • Imprimir no es devolver.
    • Las variables locales solo existen en su bloque (ámbito).
Sobrecarga (overloading): mismo nombre, distinta lista de parámetros. La elige el compilador con los tipos declarados, en tres fases: coincidencia sin boxing ni varargs, luego con boxing, luego varargs. Dentro de una fase gana el método más específico. Cambiar solo el tipo de retorno no sobrecarga.
static int calcular(int x) { return x * 2; }
static double calcular(double x) { return x * 3; }
double r = calcular(5); // elige int → 10 → se amplía a 10.0
static frente a instancia: un método static pertenece a la clase, no tiene this y no puede llamar directamente a métodos ni campos de instancia sin una referencia a un objeto. Un campo static es uno solo y compartido; un campo de instancia existe por cada objeto.
1.7 Arrays
    • Longitud fija; índices de 0 a length - 1; length es un campo, no un método.
    • Fuera de rango: ArrayIndexOutOfBoundsException en ejecución. Error típico: i <= a.length.
    • for-each copia cada elemento en la variable de iteración. Con primitivos, reasignarla no cambia el array. Con objetos, puedes mutar el objeto, pero reasignar la variable no sustituye el elemento.
    • int[] b = a; copia la referencia; Arrays.copyOf(a, a.length) crea otro array.
    • a == b compara identidad; Arrays.equals(a, b) compara elementos.
    • Arrays.toString(a) para imprimir; Arrays.deepToString(m) para matrices; Arrays.sort(a) para ordenar.
    • Un int[][] es un array de arrays: las filas pueden tener longitudes distintas (jagged).
Copia superficial de matrices: Arrays.copyOf(original, n) crea un array exterior nuevo que comparte las filas.
int[][] original = {{1, 2}, {3, 4}};

copia[0][0] = 99;              // fila compartida → original[0][0] también vale 99
copia[1] = new int[]{7, 8};    // reasigna la fila de copia → original no cambia

1.8 POO esencial
    • Encapsulación: campos privados, acceso controlado por métodos.
    • Herencia: extends una sola clase; implements varias interfaces.
    • Polimorfismo / despacho dinámico: Animal a = new Perro(); a.sonido(); ejecuta Perro.sonido(). El tipo declarado decide qué métodos puedes llamar; la clase real decide qué implementación se ejecuta.
    • Sobrecarga se resuelve en compilación (tipo declarado); sobrescritura en ejecución (clase real). Por eso mostrar(Object) gana si la variable es Object texto = "Java".
    • Clase abstracta: puede tener estado, constructores y métodos implementados; no se instancia.
    • Interfaz: contrato sin estado de instancia; admite métodos default, static y private (Java 9+); no tiene constructores.
    • equals() y hashCode(): por defecto equals compara identidad. Si dos objetos son iguales por equals, deben tener el mismo hashCode; si no, HashSet y HashMap fallan al detectar duplicados. Mismo hash no implica igualdad (colisiones).

1.10 Conversiones, casting y promoción numérica
Conversión implícita (ampliación): Java la hace sola cuando no se pierde rango: byte → short → int → long → float → double y char → int.
Conversión explícita (estrechamiento): necesita un cast y puede perder información.
int a = (int) 3.9;        // 3: trunca, no redondea
int b = (int) -3.9;       // -3
byte c = (byte) 200;      // -56: desborda el rango del byte
long d = Math.round(3.5); // 4: redondeo real
Promoción en expresiones: en una operación aritmética, byte, short y char se promocionan a int.
byte x = 1, y = 2;
byte z = x + y;      // NO compila: x + y es int
x += y;              // compila: el operador compuesto incluye un cast implícito

int mal = 1_000_000 * 1_000_000;       // -727379968: desbordamiento en int
long tambienMal = 1_000_000 * 1_000_000; // igual de mal: se calcula en int y luego se amplía
long bien = 1_000_000L * 1_000_000;    // 1000000000000

System.out.println('a' + 1);          // 98: char promocionado a int
System.out.println((char) ('a' + 1)); // b
System.out.println('a' + 'b');        // 195, no "ab"
long → float es implícita pero puede perder precisión. Con double y float, la división entre cero no lanza excepción: da Infinity o NaN. Con enteros, ArithmeticException.
Por qué x + y** se convierte automáticamente a ****int****?**
La razón principal es la eficiencia del procesador (CPU) y la prevención de desbordamientos accidentales.
    • Optimización del Hardware: Las CPUs modernas (de 32 o 64 bits) están diseñadas para procesar datos en bloques del tamaño de un entero de forma nativa. Para el procesador, realizar operaciones matemáticas con tipos de datos más pequeños (como byte de 8 bits o short de 16 bits) requiere un esfuerzo extra para enmascarar los bits. Java decide que toda la aritmética básica se ejecute en el tamaño nativo más eficiente: 32 bits (int).
    • Seguridad contra el desbordamiento: Un byte solo puede almacenar números entre -128 y 127. Si sumas dos bytes legítimos, por ejemplo, 60 + 80, el resultado es 140. Si Java mantuviera el resultado como un byte, el número desbordaría inmediatamente (daría -116), provocando un error silencioso de lógica. Al promocionarlo a int, el resultado 140 se calcula de forma segura y sin perder información.
    • La exigencia del compilador: Como el resultado de x + y es físicamente un bloque de 32 bits (int), Java te prohíbe guardarlo en un contenedor de 8 bits (byte) porque existe el riesgo de que el número sea demasiado grande y se pierdan datos. Te obliga a poner el cast explícito (byte) para que firmes el contrato de: “Sé lo que hago y asumo el riesgo de perder información”.

2. ¿Por qué x += y** sí funciona (Cast implícito)?**
La razón aquí es puramente la comodidad del programador (Azúcar sintáctico) y el propósito del operador.
    • Evitar código repetitivo y farragoso: Si los operadores compuestos no hicieran el cast automático, cada vez que quisieras incrementar un byte tendrías que escribir algo tan horrible como esto:
    • java
    • edadByte = (byte) (edadByte + 1);
    • Para evitar que el código se llene de castings visualmente molestos, los creadores de Java definieron en la Especificación del Lenguaje Java (JLS §15.26.2) que un operador compuesto como E1 op= E2 equivale exactamente a E1 = (T) (E1 op E2), donde T es el tipo de datos de E1.
    • Intención clara: Cuando escribes x += y, tu intención explícita es modificar la variable x** que ya existe**, manteniendo su tipo original. El compilador entiende esa intención y asume que aceptas las consecuencias de recortar el resultado para que vuelva a encajar en el molde del byte.

1.13 Clases envoltorio y autoboxing
Cada primitivo tiene su clase: Integer, Long, Double, Character, Boolean… Las colecciones solo admiten objetos, por eso existen.
    • Autoboxing: Integer n = 5; convierte int en Integer. Unboxing: int m = n;.
    • Unboxing de null lanza NullPointerException: Integer x = null; int y = x;.
    • Long l = 1; no compila: un literal int no se convierte en Long. Usa 1L.
    • Caché de Integer de -128 a 127: == puede funcionar con 127 y fallar con 128. Compara con equals().
    • Integer.parseInt("42") devuelve int; Integer.valueOf("42") devuelve Integer (usa la caché). Ambos lanzan NumberFormatException con texto inválido.
    • Coste: boxing crea objetos; en cálculos masivos usa primitivos o IntStream.
1.14 POO completa: constructores, acceso, herencia y clases anidadas

class Producto {
    private final String nombre;
    private final double precio;

    Producto(String nombre) { this(nombre, 0.0); }   // encadenamiento

    Producto(String nombre, double precio) {
        this.nombre = nombre;   // this distingue el campo del parámetro
        this.precio = precio;

1. Mecánica de los Constructores y Revolución Java Moderno
El constructor por defecto

    • La Trampa: En el momento en que escribes cualquier constructor (por ejemplo, uno que reciba un parámetro), ese regalo desaparece inmediatamente.

El encadenamiento con this(...)** y ****super(...)**
    • this(...): Llama a otro constructor de tu misma clase para reutilizar código.
    • super(...): Invoca obligatoriamente al constructor de la clase padre para inicializar la parte heredada antes de que el hijo empiece a construirse.

    • Ahora: Gracias a cambios modernos en el lenguaje, puedes poner código antes de super(...) siempre y cuando ese código no intente usar la palabra clave this de ninguna manera [🌍]. Esto sirve para validar datos antes de llamar al padre.

    Hijo(int valor) {
        int validado = valor < 0 ? 0 : valor; // ✅ Permitido en Java moderno
        super(validado); // El objeto padre se inicializa después de procesar el dato
    }

2. La Trampa del Orden de Inicialización
Cuando creas una instancia de una clase hija (Hijo h = new Hijo();), Java sigue un orden estrictamente jerárquico. Grábate este orden de memoria:
Paso 1: Carga Estática (Ocurre solo una vez al iniciar el programa)
    1. Se ejecutan variables y bloques static del Padre.
    2. Se ejecutan variables y bloques static del Hijo.
Paso 2: Construcción del Objeto (Ocurre cada vez que haces new)
    3. Se asignan los valores de los campos (atributos) normales de la clase Padre.
    4. Se ejecuta el cuerpo del constructor del Padre.
    5. Se asignan los valores de los campos (atributos) normales de la clase Hijo.
    6. Se ejecuta el cuerpo del constructor del Hijo.
🚨 Por qué nunca debes llamar a un método sobrescribible en un constructor:
Mira este código trampa clásico de examen:
java
class Padre {
    Padre() {
        mostrar(); // ⚠️ Llamando a un método que el hijo va a sobrescribir
    }
    void mostrar() { System.out.println("Padre"); }
}

class Hijo extends Padre {
    String texto = "Hola"; // Atributo del hijo

    @Override
    void mostrar() { System.out.println(texto.toLowerCase()); }
}
Si haces new Hijo();, el programa lanzará un NullPointerException.
    • ¿Por qué? Siguiendo el orden, el constructor de Padre (Paso 4) se ejecuta antes de que a la variable texto del hijo se le asigne el valor "Hola" (Paso 5).
    • Al llamar a mostrar(), se ejecuta la versión del Hijo (por polimorfismo), pero en ese momento exacto la variable texto del hijo todavía vale null.

3. Modificadores de Acceso y Reglas de Oro de Sobrescritura
Tabla de Accesibilidad resumida:
    1. private: Solo visible dentro de la misma clase.
    2. sin modificador (Package-Private): Solo visible por clases en el mismo paquete/carpeta.
    3. protected: Visible en el mismo paquete y por cualquier clase hija en otros paquetes.
    4. public: Visible desde cualquier parte del proyecto.
Leyes estrictas para poder usar @Override
Si vas a sobrescribir un método del padre en el hijo, debes cumplir esto a rajatabla o el compilador arrojará un error:
    • Firma idéntica: Mismo nombre de método y mismos parámetros.
    • Visibilidad: No puedes reducirla. Si el padre es protected, tu hijo no puede ser private o package-private. Debe ser protected o public.
    • Retorno Covariante: El hijo puede devolver el mismo tipo que el padre o un subtipo (ej. si el padre devuelve Animal, el hijo puede devolver Perro).
    • Excepciones: El hijo no puede lanzar excepciones controladas (checked exceptions) que sean más genéricas o nuevas que las del padre.
Las tres grandes excepciones del Polimorfismo:
    1. Métodos static** (Ocultación / Hiding):** Los métodos estáticos pertenecen a la clase, no a los objetos. No se sobrescriben. Si creas el mismo método estático en el hijo, el compilador decidirá cuál usar basándose puramente en el tipo de variable declarada.
    2. Métodos private: Como el hijo no puede verlos, no los hereda. Por lo tanto, no los puede sobrescribir. Si creas uno igual en el hijo, es un método totalmente nuevo e independiente.
    3. Los campos (atributos) NO son polimórficos: El polimorfismo solo aplica a métodos.
java
Animal a = new Perro();
System.out.println(a.nombre); // ⚠️ Imprime el campo de ANIMAL, no el de Perro.

4. Composición frente a Herencia
    • Herencia (is-a** / Es un):** Se usa cuando una clase es lógicamente una extensión de otra. Un Perro es un Animal.
    • Composición (has-a** / Tiene un):** Se usa cuando una clase utiliza a otra como una pieza de su estructura. Un Coche tiene un Motor.
¿Por qué el desarrollo moderno prefiere Composición?
La herencia rompe el encapsulamiento. Si modificas un método en la clase Padre, puedes romper el comportamiento de cientos de clases Hijo sin darte cuenta. Con la composición, el acoplamiento es bajo; puedes cambiar el comportamiento del coche simplemente inyectándole un motor diferente (ej. un MotorElectrico en lugar de un MotorCombustion) en tiempo de ejecución.

1. ¿Java pasa los objetos por referencia?
Concepto fundamental
Respuesta de entrevista:
No. Java siempre pasa los argumentos por valor (pass-by-value). Cuando pasamos un objeto a un método, lo que se copia es el valor de la referencia que apunta a ese objeto, no el objeto en sí.
Ejemplo:
class Person {
    String name;

    Person(String name) {
        this.name = name;
    }
}

public class Main {

    static void modify(Person person) {
        person.name = "Pedro";
    }

    static void replace(Person person) {
        person = new Person("Carlos");
    }

    public static void main(String[] args) {

        Person p = new Person("Juan");

        modify(p);
        System.out.println(p.name);

        replace(p);
        System.out.println(p.name);
    }
}
Resultado:
Pedro
Pedro
¿Por qué?
Cuando ejecutamos modify(p):
    1. Se copia el valor de la referencia de p.
    2. Tanto p como person apuntan al mismo objeto.
    3. Modificar sus atributos modifica el objeto original.
Cuando ejecutamos replace(p):
    1. Se copia nuevamente la referencia.
    2. person recibe una nueva referencia a otro objeto.
    3. La variable original p sigue apuntando al objeto anterior.
Concepto que debes recordar: Java siempre pasa por valor. En el caso de los objetos, el valor copiado es una referencia.
2. ¿Qué diferencia hay entre final, inmutable y static?
Concepto fundamental
Son tres conceptos diferentes que pueden combinarse.
final
Es un modificador que impide determinadas modificaciones dependiendo de dónde se aplique.
    • Variable primitiva: no puedes cambiar su valor.
    • Referencia a objeto: no puedes reasignar la referencia.
    • Método: no puedes sobrescribirlo en una subclase.
    • Clase: no puedes heredar de ella.
Ejemplo:
final int number = 10;

// Error de compilación
number = 20;
Con objetos:
final Person person = new Person("Juan");

person.name = "Pedro"; // Permitido

// Error de compilación
person = new Person("Carlos");
Importante: final no convierte automáticamente un objeto en inmutable.
Inmutable (Immutable)
Un objeto es inmutable cuando su estado no puede modificarse después de su creación.
Ejemplo:
public final class Person {

    private final String name;

    public Person(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}
Aquí:
    • La clase es final, por lo que no puede heredarse.
    • El atributo es private final.
    • No existen setters.
    • El estado no puede modificarse desde fuera.
Hay que tener cuidado con los atributos mutables: si una clase contiene una lista, por ejemplo, también debemos proteger esa lista para garantizar la inmutabilidad real.
static
Indica que un miembro pertenece a la clase y no a una instancia concreta.
Ejemplo:
public class Counter {

    static int count = 0;

    public Counter() {
        count++;
    }
}
Uso:
new Counter();
new Counter();
new Counter();

System.out.println(Counter.count);
Resultado:
3
Todas las instancias comparten el mismo atributo estático.
Resumen

3. ¿Por qué count++ no es atómico?
Importante en concurrencia
Respuesta de entrevista:
Porque count++ no es una única operación indivisible. Conceptualmente implica tres operaciones:
    1. Leer el valor actual.
    2. Incrementarlo.
    3. Escribir el nuevo valor.
Si varios hilos ejecutan simultáneamente estas operaciones, pueden producirse condiciones de carrera (race conditions).

    private int count = 0;

        count++;

    }
}

Existen diferentes alternativas.
Opción 1: synchronized

}

4. ¿Qué diferencia hay entre sobrecarga y sobrescritura y cuándo se resuelve cada una?
Concepto fundamental
Son dos mecanismos relacionados con el polimorfismo en Java.
Sobrecarga (Overloading)
Consiste en tener varios métodos con el mismo nombre, pero diferentes parámetros.
La diferencia puede estar en:
    • Número de parámetros.
    • Tipo de parámetros.
    • Orden de los parámetros.
Ejemplo:
public class Calculator {

    public int sum(int a, int b) {
        return a + b;
    }

    public int sum(int a, int b, int c) {
        return a + b + c;
    }

    public double sum(double a, double b) {
        return a + b;
    }
}
Uso:
Calculator calculator = new Calculator();

calculator.sum(2, 3);
calculator.sum(2, 3, 4);
calculator.sum(2.5, 3.5);
El compilador determina qué método utilizar basándose en los argumentos y sus tipos.
Esto se conoce como resolución estática o en tiempo de compilación.
Importante: cambiar únicamente el tipo de retorno no constituye una sobrecarga válida.
Sobrescritura (Overriding)
Consiste en redefinir en una subclase un método heredado de su clase padre.
Ejemplo:
class Animal {

    public void makeSound() {
        System.out.println("Sonido genérico");
    }
}

class Dog extends Animal {

    @Override
    public void makeSound() {
        System.out.println("Guau");
    }
}
Uso:
Animal animal = new Dog();

animal.makeSound();
Resultado:
Guau
¿Por qué?
Aunque la referencia sea de tipo Animal, el objeto real es de tipo Dog.
Java determina qué implementación ejecutar en tiempo de ejecución (runtime).
Esto se conoce como polimorfismo dinámico.

5. ¿Qué contrato une equals() y hashCode() y qué pasa si lo rompes?
Muy importante en Java Collections
Respuesta de entrevista:
El contrato establece que si dos objetos son iguales según equals(), deben devolver necesariamente el mismo valor mediante hashCode().
Es decir:
a.equals(b) == true
Implica:
a.hashCode() == b.hashCode()
Sin embargo, lo contrario no tiene por qué cumplirse.
Dos objetos pueden tener el mismo hashCode() y no ser iguales.
Esto se conoce como una colisión (hash collision).
Ejemplo
Imagina una clase Person:
public class Person {

    private String name;

    public Person(String name) {
        this.name = name;
    }

    @Override
    public boolean equals(Object obj) {

        if (this == obj) return true;

        if (!(obj instanceof Person)) return false;

        Person other = (Person) obj;

        return name.equals(other.name);
    }

    @Override
    public int hashCode() {
        return name.hashCode();
    }
}
Ahora:
Person p1 = new Person("Juan");
Person p2 = new Person("Juan");

System.out.println(p1.equals(p2));
System.out.println(p1.hashCode() == p2.hashCode());
Resultado:
true
true
¿Qué ocurre si rompemos el contrato?
Imagina que sobrescribimos equals() pero no hashCode().
Dos objetos pueden considerarse iguales, pero generar hashes diferentes.
Esto puede provocar comportamientos inesperados en estructuras como:
    • HashMap
    • HashSet
    • Hashtable
Por ejemplo:
Set<Person> people = new HashSet<>();

people.add(p1);
people.add(p2);

System.out.println(people.size());
Si los objetos son iguales según equals(), pero tienen hashes diferentes, el HashSet podría almacenarlos como elementos separados.
Regla práctica: siempre que sobrescribas equals(), sobrescribe también hashCode().
6. ¿Cuándo crearías una excepción checked y cuándo una unchecked?
Muy habitual en Spring Boot
Java distingue principalmente dos categorías de excepciones.
Checked Exceptions
Son excepciones verificadas por el compilador.
El método que puede producirlas debe:
    • Capturarlas mediante try-catch.
    • Declararlas mediante throws.
Ejemplo:
public void readFile() throws IOException {

    FileReader reader = new FileReader("data.txt");

}
IOException es una excepción checked.
¿Cuándo utilizarla?
Cuando existe una condición excepcional que el código consumidor puede gestionar razonablemente y quieres obligarlo a considerar esa posibilidad.
Ejemplos:
    • Errores de lectura de archivos.
    • Errores de comunicación con determinados recursos externos.
    • Operaciones de entrada/salida.
Unchecked Exceptions
Son excepciones que heredan de RuntimeException.
No requieren declaración ni captura obligatoria.
Ejemplo:
public void divide(int a, int b) {

    if (b == 0) {
        throw new IllegalArgumentException(
            "El divisor no puede ser cero"
        );
    }

    System.out.println(a / b);
}
¿Cuándo utilizarla?
Para representar errores de programación, violaciones de precondiciones o situaciones que normalmente no requieren que el consumidor esté obligado a capturarlas.
Ejemplos:
    • NullPointerException.
    • IllegalArgumentException.
    • IllegalStateException.
¿Y en Spring Boot?
Es habitual crear excepciones personalizadas unchecked.
Ejemplo:
public class UserNotFoundException extends RuntimeException {

    public UserNotFoundException(String message) {
        super(message);
    }
}

public User findUser(Long id) {

            .status(HttpStatus.NOT_FOUND)
            .body(ex.getMessage());
    }
}
Esto permite centralizar el tratamiento de errores y devolver respuestas HTTP coherentes.

Parte 2 — Estructuras de datos y algoritmos
Elegir una estructura es elegir qué operaciones serán baratas. Esta parte resume complejidad, búsquedas, estructuras secuenciales, conjuntos y mapas, ordenación, recursividad, árboles y método de resolución.
2.0 Cimientos: qué son las estructuras de datos y los algoritmos
Dos ideas que sostienen toda esta parte
    • Una estructura de datos es una forma de organizar información en memoria para que ciertas operaciones sean fáciles. Igual que en casa organizas cosas de forma distinta según cómo las usas: los libros en una estantería ordenados por autor, los calcetines sueltos en un cajón, los contactos en una agenda por orden alfabético.
    • Un algoritmo es una secuencia finita de pasos que resuelve un problema. Una receta es un algoritmo: ingredientes (entrada), pasos (proceso) y plato (salida).
La misma tarea se puede hacer con estructuras y algoritmos distintos, y la diferencia puede ser enorme: buscar un nombre en una agenda ordenada es rápido; buscarlo en un montón de papeles sueltos obliga a mirarlos todos.
Cómo es la memoria, a grandes rasgos
Imagina la memoria del ordenador como una calle muy larga de casillas numeradas, cada una con su dirección. Hay dos formas básicas de guardar una colección de datos ahí:
    • Contigua (un array): todos los elementos uno detrás de otro. Si sabes dónde empieza y qué posición quieres, calculas la dirección al instante: acceso directo, como ir al número 25 de una calle.
    • Enlazada (una lista enlazada): cada elemento está donde haya hueco y guarda la dirección del siguiente, como una búsqueda del tesoro donde cada pista te dice dónde está la próxima. Para llegar al quinto tienes que pasar por los cuatro anteriores.
Todas las estructuras de esta parte son combinaciones o variaciones de estas dos ideas.
Las operaciones que importan
Al elegir estructura, pregúntate qué vas a hacer más a menudo:

Pregunta

¿necesito el elemento de la posición i?

Ninguna estructura es la mejor en todo. Un array accede al instante pero insertar en medio obliga a desplazar elementos; una lista enlazada inserta fácil si ya estás en el sitio, pero acceder por posición es lento.
Medir la eficiencia contando pasos
No medimos en segundos (depende del ordenador), sino en cuántos pasos hace el algoritmo según el tamaño de la entrada, que llamamos n.
Ejemplo: buscar un número en una lista desordenada mirando uno a uno. Si hay 10 elementos, como mucho miras 10. Si hay un millón, como mucho un millón. Los pasos crecen igual que n: decimos que es O(n), “de orden n” o lineal.
Otro ejemplo: comparar cada elemento con todos los demás para buscar duplicados. Con 10 elementos son unas 100 comparaciones; con 1.000, un millón. Al multiplicar n por 10, el trabajo se multiplica por 100: O(n²), cuadrático.
Qué es un logaritmo, sin fórmulas
Aparece mucho: log₂ n es “cuántas veces puedo dividir n entre 2 hasta llegar a 1”.
    • 8 → 4 → 2 → 1: tres divisiones, así que log₂ 8 = 3.
    • 1.000 → unas 10 divisiones. 1.000.000 → unas 20.
Un algoritmo O(log n) descarta la mitad del problema en cada paso. Es el juego de “adivina el número del 1 al 100”: si te dicen “mayor” o “menor”, lo encuentras como mucho en 7 intentos. Por eso la búsqueda binaria es tan rápida.
Recordatorio: referencias
En Java las estructuras (listas, mapas, nodos) son objetos y las variables contienen referencias a ellos (ver 1.2). Un nodo de una lista enlazada no “contiene” al siguiente: guarda una referencia que apunta a él. Si entiendes Caja b = a; de la parte 1, entiendes cómo se enlazan los nodos.

Operaciones frente a tiempo real, y complejidad espacial
Big O mide cómo crece el trabajo, no cuántos milisegundos tarda. Por eso:
    • Para entradas pequeñas, un algoritmo O(n²) con constantes bajas puede ganar a uno O(n log n) (por eso Arrays.sort usa inserción en tramos pequeños).
    • La memoria caché importa: recorrer un array contiguo es mucho más rápido que saltar entre nodos de una lista enlazada, aunque ambos sean O(n).
    • Para afirmar que algo es más rápido hay que medir con un benchmark fiable (JMH en Java), no con un System.currentTimeMillis() alrededor de una llamada.

2.2 Búsqueda lineal y binaria
static int binaria(int[] a, int objetivo) {
    int izq = 0, der = a.length - 1;
    while (izq <= der) {
        int medio = izq + (der - izq) / 2; // evita desbordamiento
        if (a[medio] == objetivo) return medio;
        if (a[medio] < objetivo) izq = medio + 1;
        else der = medio - 1;
    }
    return -1;
}
    • Requiere datos ordenados por el mismo criterio de búsqueda.
    • Coste O(log n): un millón de elementos se resuelve en unas 20 comparaciones.
    • izq + (der - izq) / 2 evita el desbordamiento de (izq + der) / 2 con arrays enormes. Es una pregunta clásica.
    • En Java ya existe: Arrays.binarySearch(a, x) y Collections.binarySearch(lista, x). Si no encuentra el valor, devuelve un negativo que codifica el punto de inserción.
Corrección: en el ejercicio con {2, 5, 8, 12, 16, 23, 38} buscando 16, respondiste “continuar por la izquierda” y el asistente dijo “Correcto: A”. Tu respuesta era incorrecta: como 16 > 12, se continúa por la derecha (índices 4 a 6).

2.4 Pilas y colas
    • Pila (LIFO): el último en entrar sale primero. Usos: deshacer, pila de llamadas, paréntesis balanceados, recorrido en profundidad (DFS).

2.7 Recursividad y árboles
Toda recursión necesita un caso base y un caso recursivo que se acerque a él. Cada llamada ocupa un marco en la pila; demasiadas llamadas provocan StackOverflowError.
static int factorial(int n) {
    if (n <= 1) return 1;         // caso base
    return n * factorial(n - 1);  // caso recursivo
}
// Tiempo O(n), espacio de pila O(n)
Fibonacci ingenuo es O(2ⁿ) porque recalcula subproblemas. Con memoización (guardar resultados en un mapa o array) baja a O(n): es la idea base de la programación dinámica.
Árbol binario de búsqueda (BST): menores a la izquierda, mayores a la derecha. Equilibrado: O(log n) para buscar, insertar y borrar. Degenerado en cadena: O(n). TreeMap y TreeSet usan un árbol rojo-negro, que se mantiene equilibrado.

// two-sum: índices de dos números que suman objetivo, O(n)
static int[] twoSum(int[] nums, int objetivo) {
    Map<Integer, Integer> vistos = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        Integer j = vistos.get(objetivo - nums[i]);
        if (j != null) return new int[]{j, i};
        vistos.put(nums[i], i);
    }
    return new int[0];
}

Lista simplemente enlazada con cabeza y cola
class ListaEnlazada<T> {
    private static class Nodo<T> {
        T valor;
        Nodo<T> siguiente;
        Nodo(T valor) { this.valor = valor; }
    }

    private Nodo<T> cabeza, cola;
    private int tamano;

    void addFirst(T v) {                 // O(1)
        Nodo<T> n = new Nodo<>(v);
        n.siguiente = cabeza;
        cabeza = n;
        if (cola == null) cola = n;
        tamano++;
    }

    void addLast(T v) {                  // O(1) gracias a la referencia a la cola
        Nodo<T> n = new Nodo<>(v);
        if (cola == null) { cabeza = cola = n; }
        else { cola.siguiente = n; cola = n; }
        tamano++;
    }

    boolean remove(T v) {                // O(n): hay que buscar el nodo y su anterior
        Nodo<T> anterior = null, actual = cabeza;
        while (actual != null && !Objects.equals(actual.valor, v)) {
            anterior = actual;
            actual = actual.siguiente;
        }
        if (actual == null) return false;
        if (anterior == null) cabeza = actual.siguiente;
        else anterior.siguiente = actual.siguiente;
        if (actual == cola) cola = anterior;
        tamano--;
        return true;
    }
}
Casos límite que debes comprobar: lista vacía, borrar la cabeza, borrar la cola y borrar el único elemento.
Pila con array redimensionable
class Pila {
    private int[] datos = new int[8];
    private int tope = 0;

    void push(int x) {                   // O(1) amortizado
        if (tope == datos.length) datos = Arrays.copyOf(datos, datos.length * 2);
        datos[tope++] = x;
    }
    int pop() {
        if (tope == 0) throw new NoSuchElementException("Pila vacía");
        return datos[--tope];
    }
    int peek() {
        if (tope == 0) throw new NoSuchElementException("Pila vacía");
        return datos[tope - 1];
    }
}
Una cola se implementa igual con dos índices (frente y final) que avanzan en círculo con % capacidad: así funciona internamente ArrayDeque.
Paréntesis balanceados
static boolean balanceado(String s) {
    Deque<Character> pila = new ArrayDeque<>();
    for (char c : s.toCharArray()) {
        switch (c) {
            case '(', '[', '{' -> pila.push(c);
            case ')' -> { if (pila.isEmpty() || pila.pop() != '(') return false; }
            case ']' -> { if (pila.isEmpty() || pila.pop() != '[') return false; }
            case '}' -> { if (pila.isEmpty() || pila.pop() != '{') return false; }
            default -> { }
        }
    }
    return pila.isEmpty();              // si quedan aperturas, faltan cierres
}
Ordenación por inserción (O(n²), O(n) si ya está casi ordenado)
static void insercion(int[] a) {
    for (int i = 1; i < a.length; i++) {
        int actual = a[i];
        int j = i - 1;
        while (j >= 0 && a[j] > actual) {   // desplaza los mayores a la derecha
            a[j + 1] = a[j];
            j--;
        }
        a[j + 1] = actual;
    }
}
Merge sort (O(n log n) siempre, estable, memoria O(n))
static void mergeSort(int[] a, int izq, int der) {   // der exclusivo
    if (der - izq < 2) return;
    int medio = (izq + der) >>> 1;
    mergeSort(a, izq, medio);
    mergeSort(a, medio, der);
    int[] tmp = new int[der - izq];
    int i = izq, j = medio, k = 0;
    while (i < medio && j < der) tmp[k++] = a[i] <= a[j] ? a[i++] : a[j++]; // <= lo hace estable
    while (i < medio) tmp[k++] = a[i++];
    while (j < der) tmp[k++] = a[j++];
    System.arraycopy(tmp, 0, a, izq, tmp.length);
}
// Uso: mergeSort(a, 0, a.length);
Quicksort con partición de Lomuto (O(n log n) medio, O(n²) peor, in situ)
static void quickSort(int[] a, int lo, int hi) {     // hi inclusivo
    if (lo >= hi) return;
    int pivote = a[hi], i = lo;
    for (int j = lo; j < hi; j++) {
        if (a[j] < pivote) { int t = a[i]; a[i] = a[j]; a[j] = t; i++; }
    }
    int t = a[i]; a[i] = a[hi]; a[hi] = t;          // pivote a su posición final
    quickSort(a, lo, i - 1);
    quickSort(a, i + 1, hi);
}
// Uso: quickSort(a, 0, a.length - 1);
Con el último elemento como pivote, un array ya ordenado provoca el peor caso. Elegir un pivote aleatorio o la mediana de tres lo evita en la práctica.
Árbol binario de búsqueda
class Arbol {
    private static class Nodo {
        int valor;
        Nodo izq, der;
        Nodo(int valor) { this.valor = valor; }
    }
    private Nodo raiz;

    void insertar(int v) { raiz = insertar(raiz, v); }

    private Nodo insertar(Nodo n, int v) {
        if (n == null) return new Nodo(v);
        if (v < n.valor) n.izq = insertar(n.izq, v);
        else if (v > n.valor) n.der = insertar(n.der, v);   // duplicados ignorados
        return n;
    }

    boolean contiene(int v) {                // iterativo: O(altura)
        Nodo n = raiz;
        while (n != null) {
            if (v == n.valor) return true;
            n = v < n.valor ? n.izq : n.der;
        }
        return false;
    }

    int altura() { return altura(raiz); }
    private int altura(Nodo n) {             // en aristas: árbol vacío -1, una hoja 0
        return n == null ? -1 : 1 + Math.max(altura(n.izq), altura(n.der));
    }

    void inorden(Nodo n, List<Integer> salida) {
        if (n == null) return;
        inorden(n.izq, salida);
        salida.add(n.valor);
        inorden(n.der, salida);
    }
}
Recorrido por niveles (BFS): mete la raíz en una ArrayDeque, y mientras no esté vacía saca un nodo, procésalo y mete sus hijos. Es la base para calcular la profundidad mínima o imprimir nivel a nivel.

Parte 3 — Java avanzado, concurrencia y testing
Esta parte condensa los bloques 1 a 23 de Java avanzado: lo que se usa a diario en un backend Java y lo que más se pregunta en entrevistas de nivel junior y medio.
3.0 Cimientos: las ideas nuevas de esta parte, explicadas desde cero
Esta parte usa siete ideas que no aparecen en la programación básica. Aquí se explica cada una con calma antes de entrar en detalle.
Idea 1: la interfaz, un contrato
Una interfaz dice qué debe saber hacer algo, sin decir cómo. Es como un enchufe: cualquier aparato con la clavija correcta funciona, da igual si es una lámpara o un cargador.
interface Notificador {               // el contrato: quien lo cumpla sabe enviar
    void enviar(String mensaje);
}

class NotificadorEmail implements Notificador {     // una forma de cumplirlo
    public void enviar(String mensaje) { System.out.println("Email: " + mensaje); }
}

class NotificadorSms implements Notificador {       // otra forma
    public void enviar(String mensaje) { System.out.println("SMS: " + mensaje); }
}

Notificador n = new NotificadorSms();   // la variable es del tipo del contrato
n.enviar("Hola");                       // SMS: Hola
El código que usa Notificador no necesita saber cuál de los dos recibe. Esta idea sostiene las lambdas, Spring y el diseño SOLID.
Idea 2: genéricos, cajas con etiqueta
Antes de los genéricos, una lista guardaba Object (cualquier cosa) y al sacar un elemento tenías que convertirlo a mano, con riesgo de error en ejecución. Un genérico es un parámetro de tipo: le dices a la caja qué va a contener y el compilador vigila.
List<String> nombres = new ArrayList<>();   // "lista de String"
nombres.add("Ana");
// nombres.add(42);       ← error de compilación: 42 no es String
String primero = nombres.get(0);            // sin conversiones
Puedes crear tus propias clases genéricas. T es un nombre provisional para “el tipo que me digan”:
class Caja<T> {
    private T contenido;
    void guardar(T cosa) { contenido = cosa; }
    T sacar() { return contenido; }
}

Caja<Integer> cajaNumeros = new Caja<>();
cajaNumeros.guardar(5);
Idea 3: lambdas, pasar comportamiento como si fuera un dato
Hasta ahora pasabas datos a los métodos (números, textos, objetos). A veces quieres pasar una acción: “ordena esta lista según este criterio”, “filtra con esta condición”. Para eso existe la lambda: una función corta sin nombre.
Veamos la evolución. Queremos ordenar nombres por longitud. Comparator es una interfaz con un único método compare.
// 1) Con una clase anónima (forma antigua y larga)
nombres.sort(new Comparator<String>() {
    public int compare(String a, String b) {
        return Integer.compare(a.length(), b.length());
    }
});

// 2) Con una lambda: lo mismo, solo lo esencial
nombres.sort((a, b) -> Integer.compare(a.length(), b.length()));

// 3) Con una referencia a método y Comparator.comparing
nombres.sort(Comparator.comparing(String::length));
Cómo se lee una lambda: (parámetros) -> resultado. x -> x * 2 es “dado x, devuelve x por 2”. Si el cuerpo tiene varias líneas, va entre llaves con return.
Una lambda solo puede usarse donde se espera una interfaz funcional (una interfaz con un único método abstracto), porque así Java sabe qué método está implementando.
Idea 4: Streams, una cadena de montaje
Un Stream procesa una colección como una cadena de montaje: los elementos pasan por estaciones (filtrar, transformar, ordenar) y al final se recogen.
List<Integer> numeros = List.of(5, 12, 8, 21, 3);

// Con un bucle clásico
List<Integer> resultado = new ArrayList<>();
for (int n : numeros) {
    if (n > 6) resultado.add(n * 10);
}

// Con un Stream: se lee como una frase
List<Integer> resultado2 = numeros.stream()
    .filter(n -> n > 6)        // estación 1: deja pasar los mayores que 6 → 12, 8, 21
    .map(n -> n * 10)          // estación 2: multiplica por 10 → 120, 80, 210
    .toList();                 // recoger el resultado
Ambos dan [120, 80, 210]. El Stream no modifica la lista original.
Idea 5: hilos, varios cocineros en la misma cocina
Un programa normal hace una cosa detrás de otra: un solo hilo de ejecución. Con varios hilos, el programa puede hacer varias tareas a la vez, como una cocina con varios cocineros.
Ventaja: mientras un hilo espera una respuesta lenta (de la red o del disco), otro sigue trabajando. Problema: si dos cocineros usan la misma sartén a la vez sin coordinarse, el plato sale mal. En programación, cuando dos hilos modifican el mismo dato a la vez, el resultado puede ser incorrecto: es una condición de carrera. Toda la sección 3.7 trata de cómo coordinarlos.
Runnable tarea = () -> System.out.println("Hola desde " + Thread.currentThread().getName());
Thread hilo = new Thread(tarea);
hilo.start();          // empieza a ejecutarse en paralelo con main
Idea 6: tests automáticos, comprobar sin mirar
Un test es código que ejecuta tu código y comprueba que el resultado es el esperado. En lugar de probar a mano cada vez que cambias algo, ejecutas cientos de comprobaciones en segundos.
class CalculadoraTest {
    @Test                                    // marca este método como prueba
    void sumaDosNumeros() {
        Calculadora c = new Calculadora();
        int resultado = c.sumar(2, 3);       // ejecutar
        assertEquals(5, resultado);          // comprobar: si no es 5, el test falla
    }
}
Si alguien rompe sumar mañana, este test se pone rojo y avisa antes de que el fallo llegue a producción.
Idea 7: Maven, la lista de la compra y la receta de construcción
Un proyecto real usa bibliotecas de otras personas (para tests, para acceder a bases de datos, para web). Maven es una herramienta que:

    2. Las descarga automáticamente de internet, con las que ellas necesiten a su vez.

3.2 Streams
Un Stream es una tubería de procesamiento, no una colección. No modifica la fuente y solo puede consumirse una vez.
Intermedias (perezosas)
Terminales (ejecutan)

    .filter(p -> p.getImporte() > 100)
    .collect(Collectors.groupingBy(Pedido::getEstado, Collectors.counting()));

3.3 Optional
Representa un valor que puede faltar. Úsalo sobre todo como tipo de retorno de búsquedas.
Usuario u = repo.findById(id)
    .orElseThrow(() -> new UsuarioNoEncontradoException(id));

String nombre = repo.findById(id)
    .map(Usuario::getNombre)
    .orElse("Anónimo");
    • Optional.of(null) lanza NPE; Optional.ofNullable(x) acepta null.
    • orElse(calcular()) siempre evalúa calcular(); orElseGet(() -> calcular()) solo si falta el valor.
    • Evita get() sin comprobar. No uses Optional en campos de entidades, parámetros ni colecciones (Optional<List>): devuelve una lista vacía.
3.4 Genéricos
    • Seguridad de tipos en compilación y sin casts. class Caja<T>, static <T> T primero(List<T> l).
    • Borrado de tipos (type erasure): en ejecución List<String> y List<Integer> son la misma clase. Por eso no puedes hacer new T() ni instanceof List<String>.
    • Invarianza: List<Integer> no es subtipo de List<Number>.
    • Límites: <T extends Number>, varios con <T extends Number & Comparable<T>>.
    • PECS (Producer Extends, Consumer Super): lees de List<? extends T>, escribes en List<? super T>.
static double sumar(List<? extends Number> valores) { ... }  // acepta List<Integer>, List<Double>
static void rellenar(List<? super Integer> destino) { destino.add(1); }
3.5 Records, enums e inmutabilidad
public record UsuarioDTO(Long id, String nombre, List<String> roles) {
    public UsuarioDTO {                          // constructor compacto
        Objects.requireNonNull(nombre);
        roles = List.copyOf(roles);              // copia defensiva no modificable
    }
}
    • Un record genera constructor, accesores id(), equals, hashCode y toString. Es final y sus campos son finales. No es inmutable en profundidad si contiene objetos mutables: por eso la copia defensiva.
    • Un enum es un conjunto cerrado de constantes; admite campos, constructores, métodos e incluso implementar interfaces. Compáralos con ==. EnumMap y EnumSet son muy eficientes.
    • Clase inmutable: final, campos private final, sin setters, copias defensivas al recibir y al devolver objetos mutables. Ventajas: razonamiento sencillo y seguridad entre hilos.
3.6 Excepciones avanzadas
    • try-with-resources cierra automáticamente lo que implemente AutoCloseable, en orden inverso a su declaración, incluso si hay excepción. Si el cierre también falla, ese error queda como suppressed (e.getSuppressed()).
    • Multi-catch: catch (IOException | SQLException e).
    • Encadena causas: throw new ServicioException("No se pudo leer", e);. Nunca pierdas la excepción original.
    • No captures Exception para ignorarla. Captura donde puedas hacer algo útil; si no, propaga.
    • En Spring se prefieren excepciones de dominio unchecked gestionadas de forma centralizada (@RestControllerAdvice, parte 4).

3.8 JVM y memoria
    • javac compila a bytecode; la JVM lo interpreta y el compilador JIT convierte lo más usado en código máquina.
    • Stack (uno por hilo): marcos de llamada y variables locales. Heap (compartido): objetos y arrays. Metaspace: metadatos de clases.
    • El Garbage Collector libera objetos no alcanzables desde las raíces (variables activas, campos static). No sabes cuándo actúa; System.gc() es solo una sugerencia.
    • Fuga de memoria en Java = referencias que siguen vivas sin necesidad: colecciones static, caches sin límite, listeners no eliminados.
    • El GC no cierra ficheros ni conexiones: eso es try-with-resources.
    • Errores: StackOverflowError (recursión sin fin), OutOfMemoryError (heap agotado). Parámetros: -Xms, -Xmx.
3.9 Anotaciones y reflexión
    • Una anotación es metadato. @Retention(RUNTIME) permite leerla en ejecución; @Target limita dónde se usa.
    • La reflexión inspecciona clases en ejecución: clase.getDeclaredMethods(), metodo.getAnnotation(...).
    • Spring y Hibernate se basan en esto: escanean anotaciones como @Service o @Entity y crean objetos y proxies. Entenderlo explica “la magia” de Spring.
    • En lógica de negocio, evita la reflexión: los errores aparecen en ejecución en vez de en compilación.

3.14 Collections Framework
Jerarquía de interfaces que debes saber dibujar:
    • Iterable → Collection
        ◦ List (ordenada, admite duplicados, acceso por índice): ArrayList, LinkedList
        ◦ Set (sin duplicados): HashSet, LinkedHashSet, TreeSet (vía SortedSet / NavigableSet)
        ◦ Queue / Deque: ArrayDeque, PriorityQueue, LinkedList
    • Map (no hereda de Collection): HashMap, LinkedHashMap, TreeMap
Desde Java 21, SequencedCollection y SequencedMap añaden getFirst(), getLast() y reversed() a las colecciones con orden definido.
Programa contra la interfaz: List<String> nombres = new ArrayList<>();. Así puedes cambiar la implementación sin tocar el resto del código (DIP aplicado a colecciones).
Modificar mientras recorres (pregunta clásica):
for (String n : nombres) {
    if (n.isBlank()) nombres.remove(n);   // ConcurrentModificationException
}

nombres.removeIf(String::isBlank);       // correcto y legible

Iterator<String> it = nombres.iterator();
while (it.hasNext()) {
    if (it.next().isBlank()) it.remove(); // correcto: borra a través del iterador
}
El for-each usa un iterador por debajo; si la colección cambia por otra vía, el iterador lo detecta (fail-fast) y lanza la excepción. No tiene nada que ver con hilos.

4.0 Cimientos: qué es un backend y qué hace Spring Boot
Frontend, backend y base de datos
Una aplicación web moderna tiene tres piezas, como un restaurante:

Cómo hablan: HTTP
El frontend y el backend se comunican con HTTP, un protocolo de petición y respuesta. Cada petición lleva:
    • Método: qué quieres hacer. GET (leer), POST (crear), PUT / PATCH (modificar), DELETE (borrar).
    • URL: sobre qué recurso. https://api.tareas.com/api/v1/tareas/42.
    • Cabeceras (headers): datos extra. Content-Type: application/json, Authorization: Bearer <token>.
    • Cuerpo (body), opcional: los datos que envías, normalmente en JSON.
Y cada respuesta lleva un código de estado (200 bien, 201 creado, 400 petición incorrecta, 401 no autenticado, 404 no encontrado, 500 error del servidor), cabeceras y un cuerpo.
POST /api/v1/tareas HTTP/1.1
Content-Type: application/json

{ "titulo": "Estudiar Spring", "prioridad": 2 }

--- respuesta ---
HTTP/1.1 201 Created
Location: /api/v1/tareas/42

{ "id": 42, "titulo": "Estudiar Spring", "prioridad": 2 }
JSON es un formato de texto para datos: objetos entre { } con pares "clave": valor, listas entre [ ], textos entre comillas, números, true/false y null. Spring convierte automáticamente tus objetos Java a JSON y al revés.
Qué es una API REST
Una API (interfaz de programación) es el conjunto de URLs y reglas con las que otros programas usan tu backend. REST es un estilo para diseñarla: cada cosa es un recurso con su URL (/tareas, /tareas/42) y el método HTTP indica la acción.

Biblioteca frente a framework
    • Una biblioteca es código que tú llamas cuando quieres (como Math.max).
    • Un framework es una estructura que te llama a ti: tú escribes piezas siguiendo sus reglas y el framework decide cuándo ejecutarlas. Es la “inversión de control” de la sección 4.1.
Spring es el framework más usado en Java para backend. Spring Boot es la forma rápida de usarlo: trae configuración por defecto razonable, un servidor web integrado (Tomcat) y arranca con un main normal.
El problema que resuelve Spring
En una aplicación real, los objetos dependen unos de otros: el controlador necesita el servicio, el servicio necesita el repositorio, el repositorio necesita la conexión a la base de datos. Crear y conectar todo a mano con new en el orden correcto es tedioso y difícil de cambiar.
Spring lo hace por ti: tú marcas tus clases con anotaciones (@Service, @Repository…) y declaras en el constructor qué necesitas. Spring crea un objeto de cada una (un bean), los guarda en su contenedor y entrega a cada uno lo que pidió. Es como un montador de muebles que, con las instrucciones, sabe en qué orden encajar cada pieza.

El viaje de una petición
    1. El navegador envía GET /api/v1/tareas/42.
    2. Tomcat, el servidor web integrado, recibe la conexión.
    3. Pasa por los filtros (por ejemplo, Spring Security comprueba el token).
    4. El DispatcherServlet de Spring mira la URL y el método y elige el método del controlador que encaja.
    5. El controlador recoge los datos de la petición y llama al servicio.
    6. El servicio aplica las reglas de negocio y pide los datos al repositorio.
    7. El repositorio consulta la base de datos (con JPA/Hibernate, que genera el SQL).
    8. El resultado vuelve hacia arriba; Spring lo convierte a JSON y Tomcat envía la respuesta con su código de estado.
Si entiendes este recorrido, entiendes para qué sirve cada capa y cada anotación de las secciones siguientes.
Qué es una base de datos y un ORM
Una base de datos relacional guarda la información en tablas, como hojas de cálculo: cada fila es un registro (una tarea) y cada columna, un dato (título, prioridad). Se consulta con SQL (ver parte 10).
Un ORM (Object-Relational Mapping) traduce entre objetos Java y filas de tablas: tú trabajas con objetos Tarea y el ORM genera el SQL. En Java el estándar es JPA y la implementación más usada, Hibernate. Spring Data JPA va un paso más allá: declaras una interfaz y él escribe las consultas.
@Entity                                       // esta clase es una tabla
public class Tarea {
    @Id @GeneratedValue                       // clave primaria autogenerada
    private Long id;
    private String titulo;
    // constructor vacío, getters y setters
}

public interface TareaRepository extends JpaRepository<Tarea, Long> {
    List<Tarea> findByTituloContaining(String texto);   // Spring genera el SQL por el nombre
}
// Ya tienes gratis: save(), findById(), findAll(), deleteById()...
Y Spring Batch, ¿qué es?
Una API responde peticiones una a una, en milisegundos. Pero hay trabajos que procesan muchos datos de golpe: importar un CSV de un millón de clientes cada noche, generar facturas a fin de mes, migrar datos entre sistemas. Eso es procesamiento por lotes (batch). Spring Batch da la estructura para hacerlo de forma fiable: leer, transformar y escribir por bloques, reintentar lo que falla y continuar donde se quedó si el proceso se cae (sección 4.10).

4.1 IoC, beans e inyección de dependencias
Inversión de control: no creas tú las dependencias con new; el contenedor de Spring (ApplicationContext) crea los objetos (beans), los conecta y gestiona su ciclo de vida.
    • Estereotipos que registran beans por escaneo: @Component, @Service, @Repository (además traduce excepciones de persistencia), @Controller / @RestController.
    • @Configuration + métodos @Bean: para registrar clases que no son tuyas (un RestClient, un ObjectMapper).
    • Inyección por constructor, siempre: dependencias final, fácil de testear sin Spring y sin objetos a medio construir. Con un único constructor no hace falta @Autowired.
@Service
public class PedidoService {
    private final PedidoRepository repo;
    private final Notificador notificador;

    public PedidoService(PedidoRepository repo, Notificador notificador) {
        this.repo = repo;
        this.notificador = notificador;
    }
}
    • Varias implementaciones de una interfaz: desambigua con @Primary o @Qualifier("email"), o inyecta todas con List<Notificador> o Map<String, Notificador> (patrón Strategy).
    • Ámbitos: singleton (por defecto, una instancia por contexto), prototype (una por inyección), request y session en web. Un singleton se comparte entre todas las peticiones: no guardes estado mutable en campos de un servicio.
    • Ciclo de vida: instanciar → inyectar → @PostConstruct → en uso → @PreDestroy.
    • Proxies: @Transactional, @Cacheable y @Async funcionan porque Spring envuelve el bean en un proxy. Consecuencia clave: una llamada interna this.metodo() no pasa por el proxy y la anotación no se aplica. Tampoco funciona en métodos private.

4.5 Persistencia con JPA y Hibernate
JPA es la especificación; Hibernate, la implementación; Spring Data JPA genera repositorios.
@Entity
@Table(name = "pedidos")
public class Pedido {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "cliente_id")
    private Cliente cliente;

    @OneToMany(mappedBy = "pedido", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<LineaPedido> lineas = new ArrayList<>();

    @Version
    private Long version;   // bloqueo optimista

    protected Pedido() {}   // JPA exige constructor sin argumentos
}

public interface PedidoRepository extends JpaRepository<Pedido, Long> {
    List<Pedido> findByEstadoAndFechaAfter(Estado estado, LocalDate fecha);  // consulta derivada

Una entidad managed se sincroniza sola con la base de datos al hacer flush (dirty checking): no necesitas llamar a save para guardar cambios dentro de una transacción.

4.6 Transacciones
@Transactional en el servicio delimita una unidad de trabajo: commit al terminar, rollback si escapa una excepción.
    • Rollback por defecto solo con unchecked (RuntimeException) y Error. Para checked: @Transactional(rollbackFor = Exception.class).
    • readOnly = true en consultas: optimiza y documenta.
    • Propagación: REQUIRED (por defecto, se une a la existente o crea una), REQUIRES_NEW (suspende la actual y abre otra, útil para auditoría que debe guardarse aunque falle lo principal).
    • No funciona en llamadas internas ni en métodos privados (proxy, ver 4.1).
    • Capturar una excepción dentro del método transaccional sin relanzarla evita el rollback.
    • No hagas llamadas HTTP lentas dentro de una transacción: mantienes una conexión del pool ocupada.
Concurrencia en base de datos: bloqueo optimista con @Version (falla con OptimisticLockException si otro modificó antes; ideal con pocos conflictos) frente a pesimista con @Lock(PESSIMISTIC_WRITE) (SELECT ... FOR UPDATE; para alta contención). Niveles de aislamiento en la parte 10.
4.7 Seguridad con Spring Security
Autenticación = quién eres (401 si falla). Autorización = qué puedes hacer (403 si falla).
@Configuration
@EnableMethodSecurity
public class SeguridadConfig {
    @Bean
    SecurityFilterChain filtros(HttpSecurity http) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())   // solo en APIs sin cookies de sesión
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/v1/auth/**").permitAll()
                .requestMatchers(HttpMethod.DELETE, "/api/v1/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
            .build();
    }

    @Bean
    PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }
}
    • Spring Security es una cadena de filtros que actúa antes de llegar al controlador. El usuario autenticado vive en el SecurityContext.
    • Contraseñas: siempre hash con sal (BCrypt, Argon2). Nunca cifrado reversible ni texto plano.
    • JWT: token firmado con claims (sujeto, roles, expiración). Está firmado, no cifrado: no metas secretos. Validar firma y expiración en cada petición. Token de acceso corto + refresh token.
    • A nivel de método: @PreAuthorize("hasRole('ADMIN') or #id == authentication.name").
    • CORS se configura en Spring Security, no solo en el controlador.

4.10 Spring Batch
Spring Batch procesa grandes volúmenes de datos por lotes de forma fiable: reiniciable, transaccional y con tolerancia a fallos.
Concepto
Qué es
Job
proceso completo (“importar clientes”) formado por Steps
Step
fase del job; de tipo chunk o tasklet
JobInstance
ejecución lógica identificada por sus parámetros (fecha=2026-11-01)
JobExecution
cada intento de ejecutar una instancia
JobRepository
tablas de metadatos que guardan estado y permiten reiniciar
ItemReader / ItemProcessor / ItemWriter
leer, transformar o filtrar, escribir
Chunk
bloque de N elementos procesados en una transacción
@Bean
Step importarClientes(JobRepository repo, PlatformTransactionManager tx,
                      FlatFileItemReader<ClienteCsv> reader,
                      ClienteProcessor processor,
                      JdbcBatchItemWriter<Cliente> writer) {
    return new StepBuilder("importarClientes", repo)
        .<ClienteCsv, Cliente>chunk(500, tx)   // commit cada 500 elementos
        .reader(reader)
        .processor(processor)                  // devolver null filtra el elemento
        .writer(writer)
        .faultTolerant()
        .skip(ValidacionException.class).skipLimit(100)
        .retry(TransientDataAccessException.class).retryLimit(3)
        .build();
}

@Bean
Job importarJob(JobRepository repo, Step importarClientes) {
    return new JobBuilder("importarJob", repo).start(importarClientes).build();
}
Funcionamiento de un chunk: el reader lee elemento a elemento hasta N, el processor transforma cada uno y el writer escribe la lista completa; todo en una transacción. Si falla, se hace rollback solo de ese chunk y el JobRepository sabe hasta dónde llegó.
Decisiones de arquitectura:
    • Tamaño de chunk: más grande = menos commits y más rápido, pero rollbacks más caros y más memoria. Se mide (100 a 1.000 es un punto de partida habitual).
    • Tasklet: para un paso que es una sola tarea (borrar un fichero, llamar a un procedimiento).
    • Reinicio: una JobInstance fallida se relanza con los mismos parámetros y continúa desde el último chunk confirmado. Una completada no se repite con los mismos parámetros.
    • Skip para registros malos que no deben parar todo; retry para fallos transitorios (red, bloqueos).
    • Escalado: multi-threaded step, partitioning (dividir los datos por rangos entre workers) o remote chunking.
    • Readers y writers típicos: FlatFileItemReader (CSV), JdbcCursorItemReader / JdbcPagingItemReader, JpaPagingItemReader, JdbcBatchItemWriter.
    • Lanzamiento: planificado con @Scheduled, un cron externo o un orquestador; los parámetros identifican cada ejecución.
4.11 Spring Batch en profundidad
JobParameters y late binding: los parámetros identifican la JobInstance y se inyectan en tiempo de ejecución en beans con @StepScope o @JobScope (se crean al arrancar el step, no al arrancar la aplicación).
@Bean
@StepScope
FlatFileItemReader<ClienteCsv> reader(@Value("#{jobParameters['fichero']}") String fichero) {
    return new FlatFileItemReaderBuilder<ClienteCsv>()
        .name("clientesReader")                 // el nombre se usa para guardar su estado
        .resource(new FileSystemResource(fichero))
        .linesToSkip(1)                          // cabecera
        .delimited().names("id", "nombre", "email")
        .targetType(ClienteCsv.class)
        .build();
}
Para relanzar un job ya completado se usan parámetros distintos (fecha, identificador de ejecución) o un JobParametersIncrementer como RunIdIncrementer.
Estado entre chunks: ExecutionContext e ItemStream
    • Cada step y cada job tienen un ExecutionContext, un mapa clave-valor que el JobRepository guarda en cada commit de chunk.
    • Los readers y writers que implementan ItemStream (open, update, close) guardan ahí su posición. FlatFileItemReader guarda la línea leída; JdbcPagingItemReader, la página. Gracias a eso, un reinicio continúa donde quedó.
    • Un reader propio que deba ser reiniciable tiene que guardar su posición en update() y restaurarla en open().
    • Para pasar datos de un step a otro: guardarlos en el ExecutionContext del step y promoverlos al del job (ExecutionContextPromotionListener).
    • JdbcCursorItemReader mantiene un cursor abierto durante todo el step; los readers paginados son más seguros con varios hilos.
Listeners: JobExecutionListener (antes y después del job: notificaciones, limpieza), StepExecutionListener, ChunkListener, ItemReadListener / ItemWriteListener y SkipListener (registrar registros descartados para revisarlos).
Flujos y decisiones
new JobBuilder("importacion", repo)
    .start(validarFichero)
        .on("FAILED").to(notificarError)
    .from(validarFichero)
        .on("*").to(importarClientes)
    .next(generarInforme)

Un JobExecutionDecider permite decidir el siguiente step según datos (por ejemplo, saltar el informe si no hubo registros nuevos).

El writer debe ser idempotente cuando sea posible (upsert o comprobación por clave natural): con reintentos y reinicios, un chunk puede volver a escribirse.
Varios DataSource y gestores de transacciones
    • Es habitual separar la base de datos de metadatos de Spring Batch (JobRepository) de la base de datos de negocio.
    • El PlatformTransactionManager del step debe ser el del DataSource donde escribe el writer: es el que hace commit o rollback de cada chunk.
    • El JobRepository usa su propio gestor para los metadatos. Si ambos son distintos, un fallo entre el commit del chunk y la actualización de metadatos puede dejar datos escritos sin registrar: otra razón para writers idempotentes.
    • Marca uno de los DataSource como @Primary y nombra los demás con @Qualifier para evitar inyecciones ambiguas.
Configuración dinámica: rutas, tamaño de chunk o entidad a procesar pueden venir de JobParameters, @ConfigurationProperties o una tabla de configuración. Mantén la validación al principio (un step de validación o un JobParametersValidator) para fallar pronto y con un mensaje claro.

4.12 Spring AOP y proyecciones de Spring Data
AOP (programación orientada a aspectos) separa preocupaciones transversales (transacciones, logs, seguridad, métricas) del código de negocio. Es el mecanismo que hay detrás de @Transactional, @Cacheable y @PreAuthorize.
@Aspect
@Component
public class TiempoEjecucionAspect {
    @Around("@annotation(Cronometrado)")             // pointcut: métodos con esa anotación
    public Object medir(ProceedingJoinPoint jp) throws Throwable {
        long inicio = System.nanoTime();
        try {
            return jp.proceed();                      // ejecuta el método real
        } finally {
            log.info("{} tardó {} ms", jp.getSignature(), (System.nanoTime() - inicio) / 1_000_000);
        }
    }
}
    • Vocabulario: aspecto (la clase), advice (qué se ejecuta: @Before, @After, @Around…), pointcut (dónde), join point (la llamada concreta).
    • Spring crea un proxy: JDK dinámico si el bean implementa una interfaz, CGLIB (subclase) si no. Por eso las limitaciones de 4.1: no aplica a llamadas internas con this, ni a métodos private o final.
Proyecciones: cuando solo necesitas unos campos, no cargues la entidad entera.
public record PedidoResumen(Long id, BigDecimal total) {}

public interface PedidoRepository extends JpaRepository<Pedido, Long> {
    @Query("select new com.app.pedido.PedidoResumen(p.id, p.total) from Pedido p where p.cliente.id = :clienteId")
    List<PedidoResumen> resumenes(@Param("clienteId") Long clienteId);

    @EntityGraph(attributePaths = "lineas")          // carga las líneas en la misma consulta
    Optional<Pedido> findWithLineasById(Long id);
}
Las proyecciones evitan el N+1 y el LazyInitializationException, y reducen datos transferidos.

5.2 Objetos, arrays y referencias
Mismo modelo que Java: los primitivos se copian por valor, los objetos se manejan por referencia y los argumentos se pasan por valor (copia de la referencia).

    • Destructuring: const { nombre, edad = 18 } = usuario;, const [primero, ...resto] = lista;.

5.3 Funciones, ámbito y closures
    • Declaración (function f() {}) se eleva completa: se puede llamar antes de su línea. Expresión y flecha (const f = () => {}) no.
    • Las funciones son valores: se pasan y devuelven como cualquier objeto (funciones de orden superior).
    • Closure: una función recuerda las variables del ámbito donde se creó, aunque ese ámbito haya terminado.
function crearContador() {
  let cuenta = 0;               // privada: solo accesible desde la función devuelta
  return () => ++cuenta;
}
const siguiente = crearContador();
siguiente(); // 1
siguiente(); // 2

for (var i = 0; i < 3; i++) setTimeout(() => console.log(i)); // 3 3 3: un solo i compartido
for (let j = 0; j < 3; j++) setTimeout(() => console.log(j)); // 0 1 2: un j por iteración

5.6 Asincronía y event loop
JavaScript ejecuta tu código en un solo hilo. Las operaciones lentas (red, temporizadores) las gestiona el entorno y sus callbacks se encolan.
Orden de ejecución:
    1. Todo el código síncrono de la pila de llamadas.
    2. Todas las microtareas: callbacks de promesas (then, await), queueMicrotask.
    3. Una macrotarea: setTimeout, setInterval, eventos de E/S, eventos del DOM.
    4. Se repite: tras cada macrotarea, se vacían de nuevo las microtareas (y el navegador puede repintar).
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
console.log(4);
// Salida: 1 4 3 2

    • await dentro de un bucle for ejecuta las peticiones en serie. Para paralelo, Promise.all.
    • array.forEach(async ...) no espera a nada. Usa for...of con await o Promise.all(array.map(...)).
    • Una promesa rechazada sin catch provoca unhandledrejection.
    • Cancelación: AbortController y su signal en fetch.
Diferencia con Java: un CompletableFuture puede ejecutarse en otro hilo; una promesa de JavaScript no crea hilos, solo ordena callbacks en el único hilo.
5.7 TypeScript: fundamentos

5.11 Errores en JavaScript
    • Tipos nativos: Error, TypeError (operación sobre un tipo inválido, como llamar a algo que no es función), ReferenceError (variable inexistente o en TDZ), RangeError, SyntaxError.
    • Se puede lanzar cualquier valor, pero lanza siempre instancias de Error para conservar la pila de llamadas.
class ValidacionError extends Error {
  constructor(mensaje, campo, opciones) {
    super(mensaje, opciones);          // opciones admite { cause }
    this.name = "ValidacionError";
    this.campo = campo;
  }
}

try {
  guardar(datos);
} catch (e) {
  if (e instanceof ValidacionError) mostrarError(e.campo, e.message);
  else throw new Error("No se pudo guardar", { cause: e });   // encadena la causa
} finally {
  ocultarSpinner();
}
    • Dentro de una función async, un throw rechaza la promesa; se captura con try/catch alrededor del await o con .catch().
    • Un error dentro de un setTimeout no lo captura un try/catch exterior: cuando se ejecuta, la función que tenía el try ya terminó.

Parte 6 — React
React se resume en una frase: la interfaz es una función del estado, UI = f(estado). Casi todas las preguntas de entrevista salen de entender cuándo y por qué se vuelve a ejecutar esa función.
6.0 Cimientos: React desde cero
Requisito: haber leído 5.0 (funciones flecha, objetos, arrays, map, el DOM y npm).
Qué problema resuelve React
En 5.0 viste cómo cambiar la página a mano con el DOM: buscar el botón, cambiar su texto. Con un contador vale; con una aplicación de tareas con filtros, contadores, formularios y datos del servidor, acabas con cientos de líneas que recuerdan qué trozo de la página tocar en cada caso, y es fácil olvidar uno.
React cambia el enfoque: tú no tocas el DOM. Describes cómo debe verse la interfaz para unos datos dados, y cuando los datos cambian, React calcula qué ha cambiado y actualiza la página por ti. Es como una hoja de cálculo: escribes la fórmula una vez y la celda se recalcula sola cuando cambian los datos.
SPA: aplicación de una sola página
En una web tradicional, cada clic en un enlace pide al servidor una página HTML nueva y el navegador la recarga entera. Una SPA (Single Page Application) carga una sola página y, a partir de ahí, JavaScript cambia el contenido y pide solo datos (JSON) al backend. La navegación es más fluida, como en una app de escritorio. React y Angular se usan sobre todo para hacer SPAs.

Componentes: piezas de Lego
Una interfaz en React se construye con componentes: piezas reutilizables, cada una responsable de un trozo de pantalla. Una página de tareas podría ser App → Cabecera, FormularioTarea, ListaTareas → muchas FilaTarea.
Un componente es simplemente una función que devuelve lo que se debe mostrar. Su nombre empieza por mayúscula.
function Saludo() {
  return <h1>Hola, Juan</h1>;
}

export default function App() {
  return (
    <div>
      <Saludo />          {/* se usa como si fuera una etiqueta HTML */}
      <Saludo />          {/* y se puede reutilizar */}
    </div>
  );
}
JSX: HTML dentro de JavaScript
Eso que parece HTML dentro de la función es JSX: una sintaxis que Vite traduce a JavaScript. Reglas que debes saber:
    • Las llaves { } insertan cualquier expresión de JavaScript: <p>Tienes {tareas.length} tareas</p>.
    • Se usa className en vez de class (porque class es palabra reservada de JS) y htmlFor en vez de for.
    • Toda etiqueta se cierra: <img />, <input />.
    • Un componente devuelve un único elemento raíz; si no quieres un div de más, usa un fragmento <> ... </>.
    • Los eventos se escriben en camelCase y reciben una función: onClick={manejarClic}.
Props: los parámetros de un componente
Igual que una función recibe argumentos, un componente recibe props (propiedades) desde su padre.
function FilaTarea({ titulo, hecha }) {          // desestructuramos las props
  return <li>{hecha ? "✅" : "⬜"} {titulo}</li>;
}

function App() {
  return (
    <ul>
      <FilaTarea titulo="Estudiar React" hecha={false} />
      <FilaTarea titulo="Leer apuntes" hecha={true} />

Las props van del padre al hijo y el hijo no puede modificarlas: son de solo lectura.
Estado: la memoria del componente
Las variables normales de una función se pierden cada vez que la función termina. Para que un componente recuerde algo (un contador, el texto de un input, una lista) y la pantalla se actualice cuando cambia, se usa el estado con el hook useState.
import { useState } from "react";

function Contador() {
  const [cuenta, setCuenta] = useState(0);   // valor inicial 0
  //     ↑ valor actual  ↑ función para cambiarlo

  return (
    <button onClick={() => setCuenta(cuenta + 1)}>
      Has pulsado {cuenta} veces
    </button>
  );
}
Qué pasa al pulsar:
    1. Se llama a setCuenta(1).
    2. React guarda el nuevo valor y vuelve a ejecutar la función Contador (a esto se le llama renderizar).
    3. Esta vez cuenta vale 1, así que el JSX devuelve “Has pulsado 1 veces”.
    4. React compara con lo anterior y cambia en el DOM solo el texto del botón.
Nunca cambies el estado directamente (cuenta = 5 no hace nada visible): usa siempre la función set....

Los datos bajan, los eventos suben
El estado vive en el componente que lo necesita (o en el padre común si lo necesitan varios). Para que un hijo cambie el estado del padre, el padre le pasa una función como prop:
function FormularioTarea({ onAnadir }) {
  const [texto, setTexto] = useState("");

  function enviar(e) {
    e.preventDefault();               // evita que el formulario recargue la página
    if (texto.trim() === "") return;
    onAnadir(texto);                  // avisa al padre
    setTexto("");                     // limpia el input
  }

  return (
    <form onSubmit={enviar}>
      <input value={texto} onChange={e => setTexto(e.target.value)} placeholder="Nueva tarea" />
      <button type="submit">Añadir</button>
    </form>
  );
}

export default function App() {
  const [tareas, setTareas] = useState([]);

  function anadir(titulo) {
    setTareas([...tareas, { id: crypto.randomUUID(), titulo, hecha: false }]);  // array nuevo
  }

  return (
    <main>
      <h1>Mis tareas</h1>
      <FormularioTarea onAnadir={anadir} />
      <ListaTareas tareas={tareas} />

}
Esta mini aplicación ya contiene casi todos los conceptos base: componentes, props, estado, eventos, formulario controlado, listas con key y actualización inmutable ([...tareas, nueva] crea un array nuevo en lugar de modificar el antiguo; la razón está en 6.3).

6.1 Componentes, JSX y props
    • Un componente es una función que recibe props y devuelve JSX. Nombre en mayúsculas.
    • JSX se compila a llamadas que crean objetos que describen la UI; no es HTML (className, htmlFor, onClick).
    • Las props son de solo lectura. Los datos bajan por props; los eventos suben con callbacks pasados como props.
    • children permite componer: <Tarjeta><Titulo /></Tarjeta>.
    • Un componente debe ser puro durante el render: mismas props y estado, mismo JSX, sin efectos secundarios.
6.2 Renderizado y reconciliación
Un componente se vuelve a renderizar cuando: cambia su estado, su componente padre se renderiza, o cambia un Context que consume. Que cambien sus props no es la causa: lo es que el padre se renderice.
    1. Render: React llama a tus componentes y obtiene el nuevo árbol.
    2. Reconciliación: compara el árbol nuevo con el anterior.
    3. Commit: aplica al DOM solo las diferencias.
Reglas de identidad:
    • Mismo tipo de componente en la misma posición: se conserva el estado. Tipo distinto: se desmonta y se monta de nuevo, perdiendo el estado.
    • En listas, key identifica cada elemento entre renders. Debe ser estable y única: el id del dato. No uses el índice si la lista se reordena, filtra o inserta: el estado se mezcla entre filas.
    • Cambiar la key de un componente es la forma idiomática de reiniciar su estado.
    • No definas componentes dentro de otros componentes: cada render crea un tipo nuevo y se pierde el estado.
6.3 Estado con useState
function Contador() {
  const [count, setCount] = useState(0);

  function sumarTres() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);   // count vale 0 en las tres: resultado 1
  }

  function sumarTresBien() {
    setCount(c => c + 1);
    setCount(c => c + 1);
    setCount(c => c + 1);  // cada función recibe el valor pendiente: resultado 3
  }

  return <button onClick={sumarTresBien}>{count}</button>;
}
    • Snapshot: en cada render, count es una constante. Llamar a setCount no la cambia en ese render; programa el siguiente.
    • Batching: React agrupa todas las actualizaciones de un mismo evento en un solo render. Desde React 18 también dentro de promesas y setTimeout.
    • Actualización funcional (c => c + 1) cuando el nuevo valor depende del anterior.
    • Inmutabilidad: React compara con Object.is. Si mutas el objeto y pasas la misma referencia, puede no renderizar.
setUsuario(u => ({ ...u, edad: u.edad + 1 }));                 // objeto
setTareas(ts => [...ts, nueva]);                                // añadir
setTareas(ts => ts.filter(t => t.id !== id));                   // quitar
setTareas(ts => ts.map(t => t.id === id ? { ...t, hecha: true } : t)); // editar
    • No guardes en estado lo que puedes calcular a partir de otro estado o de las props (estado derivado): calcúlalo durante el render.
    • Inicialización costosa: useState(() => leerDeLocalStorage()).
    • Estado complejo con muchas transiciones: useReducer(reducer, inicial).

6.5 useRef, useMemo, useCallback y React.memo
    • useRef guarda un valor mutable que persiste entre renders sin provocar render al cambiar. Usos: referencia a un elemento del DOM, id de un temporizador.

6.6 Composición, Context y estado global
    • Prop drilling: pasar props a través de muchos niveles que no las usan. Primero intenta componer con children; si no basta, usa Context.
    • Context: para datos que muchos componentes leen y cambian poco (usuario autenticado, tema, idioma). Todos los consumidores se renderizan cuando cambia el valor: no lo uses para estado que cambia constantemente.
    • Hooks personalizados (useUsuario, useDebounce) extraen lógica reutilizable. Empiezan por use y siguen las reglas de los hooks.
    • Reglas de los hooks: llámalos solo en el nivel superior del componente o de otro hook; nunca dentro de condiciones, bucles ni funciones anidadas. React los identifica por su orden de llamada.

6.11 Error boundaries
Un error lanzado durante el render desmonta todo el árbol si nadie lo captura. Un error boundary lo captura y muestra una interfaz alternativa. No existe como hook: es un componente de clase (o la librería react-error-boundary).
class LimiteErrores extends React.Component {
  state = { error: null };
  static getDerivedStateFromError(error) { return { error }; }   // actualiza el estado
  componentDidCatch(error, info) { reportar(error, info.componentStack); } // registra
  render() {
    return this.state.error ? this.props.fallback : this.props.children;
  }
}

<LimiteErrores fallback={<p>Algo ha fallado</p>}>
  <Panel />
</LimiteErrores>
No captura errores de manejadores de eventos, código asíncrono (setTimeout, promesas) ni del propio boundary: esos se gestionan con try/catch y estado de error.

PARTE 1: Explicación de los Conceptos Clave
    • 1. La regla de oro: UI = f(estado)
    • Imagina que React es una fábrica de juguetes. El “estado” son los planos actuales del juguete. Cada vez que cambias un plano (cambia el estado), la fábrica vuelve a presionar el botón de producción para generar un nuevo juguete (la UI).
        ◦ Un componente no modifica el HTML directamente.
        ◦ El componente solo le dice a React: “Con estos datos actuales, el HTML debería verse así”.
    • 2. El proceso de Renderizado (Render \(\rightarrow \) Reconciliación \(\rightarrow \) Commit)
    • Cuando algo cambia, React no borra toda la pantalla y la vuelve a dibujar desde cero (eso sería lentísimo). Hace lo siguiente:
        1. Render: Ejecuta las funciones de tus componentes para generar un nuevo mapa conceptual (el árbol virtual o Virtual DOM).
        2. Reconciliación (Algoritmo Dif): Compara el mapa nuevo con el mapa viejo para ver qué ha cambiado exactamente.
        3. Commit: Va al navegador real y modifica únicamente el nodo o el texto que cambió.
    • 3. Las Claves de la Identidad (key)
    • Cuando React renderiza una lista de elementos (por ejemplo, un listado de tareas), necesita saber qué elemento es cuál si decides desordenarlos, borrarlos o añadir uno nuevo.
        ◦ El peligro del índice (index): Si usas el número de posición de la lista como key y borras el primer elemento, el que antes era el número 2 ahora pasa a ser el número 1. React se confundirá y pensará que modificaste el elemento 1 en lugar de haber borrado el anterior, mezclando los estados internos de tus componentes (como inputs o animaciones). Usa siempre un ID único de tu base de datos.
    • 4. El “Snapshot” y el Cierre del Estado (useState)
    • Cuando un componente se renderiza, las variables del estado son fijas (constantes) para ese render en específico.
Si tienes count = 0 y haces:
    • javascript
    • setCount(count + 1); // Le dice a React: "En el próximo render, count valdrá 1"
console.log(count);  // Sigue imprimiendo 0 inmediatamente, porque este render ya se congeló con 0.
    • 5. useEffect: El puente con el mundo exterior
    • React quiere ser “puro” (recibir datos y escupir HTML). Pero en el mundo real necesitas pedir datos a un servidor, activar temporizadores o escuchar eventos globales. Para eso sirve useEffect.
        ◦ La limpieza (cleanup): Si abres una conexión en un efecto, debes cerrarla al desmontar el componente o antes de que el efecto se vuelva a ejecutar. Piensa en ello como apagar la luz al salir de una habitación para no consumir recursos (evitar memory leaks).
    • 6. Rendimiento y Memoización
    • Cada vez que un componente padre se vuelve a ejecutar, todas las funciones y objetos que declaras dentro de él se vuelven a crear desde cero en la memoria del ordenador. Tienen referencias de memoria distintas.
        ◦ useMemo: Almacena el resultado de una operación matemática o lógica costosa para no repetirla.
        ◦ useCallback: Almacena la referencia de una función para que no se recree en cada render.
        ◦ React.memo: Le dice a un componente hijo: “No te vuelvas a renderizar a menos que tus props cambien realmente”

PARTE 2: Respuestas a las Preguntas de Entrevista
    • Aquí tienes las respuestas directas, técnicas y listas para defender en una entrevista laboral:
    • 1. ¿Cuándo se renderiza un componente? ¿Y por qué mutar el estado puede no renderizar?
        ◦ Cuándo se renderiza: Un componente se renderiza por tres motivos:
            1. Su propio estado interno cambia (useState, useReducer).
            2. Su componente padre se vuelve a renderizar.
            3. Un Context que el componente consume sufre una actualización en su valor.
        ◦ Por qué mutar no funciona: React utiliza una comparación estricta de referencias (Object.is) para saber si el estado cambió. Si haces algo como usuario.edad = 30 y luego setUsuario(usuario), estás modificando (mutando) el mismo objeto en la misma dirección de memoria. Para React, el objeto “es el mismo” y decide no re-renderizar para ahorrar recursos. La solución es crear una copia inmutable: setUsuario({ ...usuario, edad: 30 }).
    • 2. Explica la diferencia entre setCount(count + 1)** tres veces y ****setCount(c => c + 1)**** tres veces.**
        ◦ Caso 1 (count + 1): En un render específico, count funciona como una constante (un snapshot). Si count vale 0, las tres líneas se evalúan literalmente como setCount(0 + 1). React procesa las tres, pero el resultado final programado para el siguiente render será 1.
        ◦ Caso 2 (c => c + 1): Utiliza una actualización funcional. En lugar de pasar un valor estático, le pasas una función a React. React mete estas funciones en una cola (queue) y las ejecuta secuencialmente, pasando el valor pendiente acumulado a la siguiente función (0 -> 1 -> 2 -> 3). El resultado final será 3.
    • 3. ¿Para qué sirve key** y por qué no usar el índice?**
        ◦ Para qué sirve: La propiedad key le da una identidad estable a los elementos de una lista para que React pueda rastrearlos de manera eficiente durante la reconciliación del Virtual DOM, identificando de manera exacta qué elementos se añadieron, cambiaron de lugar o se eliminaron.
        ◦ Por qué evitar el índice: Si la lista se reordena, se filtra o se insertan elementos en medio, los índices de los elementos cambian. Esto rompe la asociación del estado interno del componente en el DOM y puede provocar errores visuales graves (por ejemplo, que un checkbox se quede marcado en la fila equivocada).
    • 4. ¿Qué hace la función de limpieza de useEffect** y cuándo se ejecuta?**
        ◦ Qué hace: Se encarga de deshacer efectos secundarios activos para evitar fugas de memoria o colisiones de datos. Sirve para abortar peticiones HTTP en curso (AbortController), limpiar setTimeout/setInterval o remover event listeners globales.
        ◦ Cuándo se ejecuta: Se ejecuta en dos momentos precisos:
            1. Justo antes de volver a ejecutar el efecto (si las dependencias cambiaron).
            2. Cuando el componente se desmonta por completo del DOM.
    • 5. ¿Por qué React.memo** no evita un render si pasas una función inline?**
        ◦ React.memo realiza una comparación superficial (shallow comparison) de las props del componente hijo.
        ◦ Si en el componente padre declaras una función inline (ej. onBorrar={() => borrar(id)}) o una función normal sin memorizar, JavaScript creará una nueva instancia de esa función en cada render con una dirección de memoria diferente.
        ◦ Al comparar las props, React.memo detecta que la referencia de la función cambió y vuelve a renderizar el componente hijo de todos modos. Para solucionarlo, esa función debe envolverse en un hook useCallback en el padre.
    • 6. Context** frente a Redux o Zustand: ¿cuándo usar cada uno?**
        ◦ Context: Es ideal para configuraciones globales, de bajo dinamismo, que cambian poco o rara vez (ej. cambiar el tema claro/oscuro, configuraciones del idioma o los datos del usuario logueado). Su problema es que cuando el valor del Context cambia, todos los componentes que lo consumen se vuelven a renderizar de forma masiva.
        ◦ Zustand / Redux Toolkit: Diseñados para gestionar estados complejos y altamente dinámicos en el cliente (ej. un carrito de compras, un editor de texto interactivo o notificaciones en tiempo real). Permiten usar selectores para que un componente se suscriba únicamente a un fragmento específico del estado global y solo se renderice cuando esa propiedad puntual cambie.
    • 7. ¿Qué son las reglas de los hooks y por qué existen?
        ◦ Cuáles son:
            1. Solo se pueden llamar hooks en el nivel superior del componente (no dentro de if, ciclos for o funciones anidadas).
            2. Solo se pueden llamar desde componentes funcionales de React o desde hooks personalizados (custom hooks).
        ◦ Por qué existen: Internamente, React no sabe el nombre de tus hooks; rastrea su estado basándose estrictamente en el orden en el que son ejecutados. Si pones un hook dentro de un condicional (if), en un render podría ejecutarse y en otro no, alterando el orden de la lista interna de React. Esto provocaría que el estado de un hook se asigne erróneamente a otro en los renders posteriores, rompiendo la aplicación por completo.

Parte 7 — Angular
Angular es un framework completo y con opiniones: trae inyección de dependencias, router, formularios y cliente HTTP. Las preguntas se centran en DI, detección de cambios, Signals y RxJS. Estos apuntes usan el Angular moderno: componentes standalone, Signals y el nuevo control de flujo.
7.0 Cimientos: Angular desde cero
Requisito: haber leído 5.0, sobre todo la parte de TypeScript (tipos, interfaces, clases).
Qué es Angular y en qué se diferencia de React
Angular es un framework de Google para construir aplicaciones web de una sola página (SPA, ver 6.0). Resuelve el mismo problema que React (no tocar el DOM a mano), pero con otra filosofía:
    • React es una biblioteca centrada en la vista: tú eliges router, cliente HTTP, formularios…
    • Angular es un framework completo: trae de serie router, cliente HTTP, formularios, inyección de dependencias, testing y una herramienta de línea de comandos. Todo proyecto Angular se parece a otro, lo que gusta mucho en empresas grandes.
    • Angular usa TypeScript obligatoriamente y separa la lógica (una clase) de la vista (una plantilla HTML).
Si vienes de Java y Spring, Angular te resultará familiar: clases, decoradores parecidos a las anotaciones, servicios e inyección de dependencias.

Anatomía de un componente
Un componente Angular es una clase TypeScript con un decorador que la conecta con una plantilla HTML y unos estilos.
import { Component, signal } from "@angular/core";

@Component({
  selector: "app-contador",          // la etiqueta con la que se usa: <app-contador />
  template: `
    <p>Has pulsado {{ cuenta() }} veces</p>
    <button (click)="incrementar()">Sumar</button>
  `,
  styles: `p { font-weight: bold; }`,
})
export class ContadorComponent {
  cuenta = signal(0);                // estado reactivo, valor inicial 0

  incrementar() {
    this.cuenta.update(c => c + 1);  // al cambiar, Angular actualiza la vista
  }
}
    • Un decorador (@Component) es una etiqueta con @ que añade información a una clase, como las anotaciones de Java (@Service). Le dice a Angular “esta clase es un componente, este es su HTML”.
    • En proyectos reales, la plantilla y los estilos suelen ir en ficheros aparte: templateUrl: "./contador.component.html", styleUrl: "./contador.component.css".
    • Un signal es una caja reactiva: se lee llamándola (cuenta()) y se cambia con .set() o .update(). Cuando cambia, Angular sabe qué partes de la pantalla dependen de ella y las actualiza. Es el equivalente a useState en React.
Las cuatro formas de conectar clase y plantilla (data binding)
<!-- 1. Interpolación: mostrar un valor -->
<h1>Hola, {{ nombre }}</h1>

<!-- 2. Property binding: dar valor a una propiedad de un elemento -->
<button [disabled]="guardando">Guardar</button>

<!-- 3. Event binding: reaccionar a un evento -->
<button (click)="guardar()">Guardar</button>

<!-- 4. Two-way binding: un input sincronizado en ambas direcciones -->
<input [(ngModel)]="nombre" />
Truco para recordarlo: corchetes [ ] = el dato entra al elemento; paréntesis ( ) = el evento sale del elemento; los dos juntos [( )] (“banana en una caja”) = ambas direcciones.

Servicios e inyección de dependencias
Los componentes deben ocuparse de la pantalla. La lógica compartida y las llamadas al servidor van en servicios: clases con @Injectable que Angular crea y entrega a quien las pida. Es exactamente la misma idea que los beans de Spring.
@Injectable({ providedIn: "root" })        // una sola instancia para toda la aplicación
export class TareaService {
  private http = inject(HttpClient);        // Angular nos da el cliente HTTP

  listar() {
    return this.http.get<Tarea[]>("/api/tareas");
  }
}

@Component({ /* ... */ })
export class ListaTareasComponent {
  private servicio = inject(TareaService);  // pedimos el servicio
  tareas = toSignal(this.servicio.listar(), { initialValue: [] });
}
Para que HttpClient funcione, se registra una vez en app.config.ts con provideHttpClient().
Observables, sin miedo
http.get no devuelve los datos, sino un Observable: un flujo de valores al que te suscribes. La diferencia con una promesa de JavaScript:
    • Una promesa es como pedir una pizza: un pedido, una entrega, fin.
    • Un observable es como una suscripción a una revista: puedes recibir muchos números a lo largo del tiempo, y puedes darte de baja. Además, si nadie se suscribe, no se envía nada.
this.servicio.listar().subscribe(tareas => {
  console.log("Han llegado", tareas.length, "tareas");
});
Los operadores de RxJS (map, filter, switchMap…) transforman esos flujos como los Streams de Java transforman colecciones. En Angular moderno, muchas veces conviertes el observable en signal con toSignal y te olvidas de suscribirte a mano. Todo el detalle, en 7.5.

7.2 Servicios e inyección de dependencias
Mismo concepto que Spring: Angular crea los servicios y los inyecta.
@Injectable({ providedIn: "root" })        // singleton para toda la app
export class TareaService {
  private http = inject(HttpClient);       // inject() o inyección por constructor
  listar() { return this.http.get<Tarea[]>("/api/tareas"); }

    • providedIn: "root": una instancia global y eliminable del bundle si nadie la usa.
    • Proveer en un componente (providers: [...]) crea una instancia por cada instancia de ese componente.
    • Los inyectores forman una jerarquía: Angular busca hacia arriba hasta encontrar un proveedor.
    • InjectionToken para inyectar valores que no son clases (configuración).
7.3 Signals
Un signal es un valor reactivo que avisa a quien lo lee cuando cambia.
export class CarritoComponent {
  items = signal<Item[]>([]);
  total = computed(() => this.items().reduce((s, i) => s + i.precio, 0)); // derivado, perezoso y memorizado

  constructor() {
    effect(() => localStorage.setItem("carrito", JSON.stringify(this.items())));
  }

  anadir(item: Item) {
    this.items.update(lista => [...lista, item]);   // inmutable, como en React
  }
}
    • signal() para estado, .set() y .update() para cambiarlo; se lee llamándolo: items().
    • computed() para valores derivados: no lo guardes en otro signal.
    • effect() solo para sincronizar con el exterior (logs, almacenamiento); no para propagar estado.
    • toSignal(observable$) y toObservable(signal) conectan Signals con RxJS.
    • Signals permiten detección de cambios de grano fino y el modo zoneless (sin Zone.js) de las versiones recientes.
7.4 Detección de cambios y OnPush
    • Por defecto, Angular revisa todo el árbol de componentes tras cada evento asíncrono, detectado por Zone.js.
    • Con OnPush, un componente solo se revisa si: cambia la referencia de un input, se dispara un evento en él, emite un observable con el pipe async, cambia un signal que lee su plantilla, o se marca manualmente.
    • Consecuencia: con OnPush, mutar un objeto de entrada (tarea.hecha = true) no actualiza la vista. Hay que crear un objeto nuevo. Es el mismo principio de inmutabilidad que en React.
    • Recomendación actual: OnPush en todos los componentes + Signals.

7.7 Routing, guards e interceptores
export const routes: Routes = [
  { path: "", component: InicioComponent },
  { path: "admin", canActivate: [adminGuard],

export const adminGuard: CanActivateFn = () =>
  inject(AuthService).esAdmin() || inject(Router).createUrlTree(["/login"]);

export const tokenInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthService).token();
  return next(token ? req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }) : req);

7.11 SSR e hidratación en Angular
    • @angular/ssr genera el HTML en el servidor; provideClientHydration() reutiliza ese DOM en el navegador en lugar de reconstruirlo.
    • Hidratación incremental con @defer (hydrate on viewport): partes de la página solo se activan cuando hacen falta.
    • En el servidor no existen window, document ni localStorage: el código que los usa debe ejecutarse solo en el navegador (afterNextRender, o comprobar la plataforma con isPlatformBrowser).
    • Ventajas: primera carga más rápida y SEO. Coste: servidor Node y cuidado con el código dependiente del navegador.

Python parece sencillo, pero las entrevistas buscan sus trampas: mutabilidad, identidad, argumentos por defecto, ámbito, el GIL y la diferencia entre async y concurrencia real. FastAPI combina type hints, Pydantic e inyección de dependencias.
8.0 Cimientos: Python y FastAPI desde cero
Qué es Python
Python es un lenguaje de propósito general famoso por su sintaxis limpia: se lee casi como pseudocódigo. Se usa para backend (FastAPI, Django), automatización, análisis de datos e inteligencia artificial. Como JavaScript, es de tipado dinámico (las variables no declaran tipo) y se ejecuta con un intérprete, sin paso de compilación visible.
Instalar y ejecutar
    1. Instala Python 3 desde python.org (en Linux y macOS suele venir instalado). Comprueba con python3 --version (en Windows, python --version).
    2. Modo interactivo: escribe python3 en la terminal y aparece >>>. Ahí pruebas líneas sueltas, como en jshell. Sales con exit().
    3. Script: crea hola.py con print("Hola, Juan") y ejecútalo con python3 hola.py.
No hace falta clase ni main: el fichero se ejecuta de arriba abajo.
La gran diferencia: la indentación es la sintaxis
En Java las llaves { } marcan los bloques. En Python los marca la sangría (cuatro espacios), y la línea que abre un bloque termina en dos puntos :. Si la indentación está mal, el programa no funciona.
edad = 20
if edad >= 18:
    print("Mayor de edad")      # dentro del if (4 espacios)
    print("Puede votar")        # también dentro
print("Fin")                    # fuera del if

FastAPI: tu primera API en Python
FastAPI es un framework para crear APIs REST (ver 4.0 para qué es una API, HTTP y JSON). Usa las anotaciones de tipo de Python para validar datos y generar documentación automática.
# main.py
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class TareaNueva(BaseModel):        # describe el JSON que esperamos recibir
    titulo: str
    prioridad: int = 1

tareas = []                          # "base de datos" en memoria, solo para aprender

@app.get("/hola")                    # GET /hola
def hola(nombre: str = "mundo"):     # ?nombre=Juan
    return {"mensaje": f"Hola, {nombre}"}   # un dict se devuelve como JSON

@app.post("/tareas", status_code=201)
def crear(tarea: TareaNueva):        # FastAPI valida el JSON del cuerpo
    nueva = {"id": len(tareas) + 1, **tarea.model_dump()}
    tareas.append(nueva)
    return nueva

@app.get("/tareas/{tarea_id}")
def obtener(tarea_id: int):          # convierte "5" de la URL en el entero 5
    return tareas[tarea_id - 1]

fastapi dev main.py                  # arranca en http://127.0.0.1:8000

Equivalencias con Spring Boot: @app.get es @GetMapping; un modelo BaseModel de Pydantic es un DTO con validación; Depends (8.8) es la inyección de dependencias.

8.1 Modelo de datos: todo es un objeto
En Python todas las variables son referencias a objetos (no hay primitivos como en Java). Lo que importa es si el objeto es mutable.
Inmutables
Mutables
int, float, bool, str, tuple, frozenset, bytes, None
list, dict, set, bytearray, objetos de clases propias
    • == compara valor (llama a __eq__); is compara identidad (mismo objeto, como == con referencias en Java). Usa is solo con None: if x is None.
    • CPython reutiliza enteros pequeños (-5 a 256): a is b puede ser True o False según el valor. No dependas de ello.
    • Asignar no copia: b = a comparte la lista. Copia superficial: a.copy(), list(a), a[:]. Profunda: copy.deepcopy(a).
    • Paso de argumentos: “por asignación” (igual que Java con referencias): la función puede mutar una lista recibida, pero reasignar el parámetro no afecta al llamador.
    • Tipado dinámico pero fuerte: "5" + 3 lanza TypeError (en JavaScript daría "53").
    • Falsy: False, None, 0, 0.0, "", [], {}, set().

8.3 Funciones y sus trampas
Argumento mutable por defecto: el valor por defecto se evalúa una sola vez, al definir la función.
def anadir(item, lista=[]):        # MAL: la misma lista en todas las llamadas
    lista.append(item)
    return lista

anadir(1)  # [1]
anadir(2)  # [1, 2]  ← sorpresa

def anadir(item, lista=None):      # BIEN
    if lista is None:
        lista = []
    lista.append(item)
    return lista
    • Ámbito LEGB: Local, Enclosing (función contenedora), Global, Built-in. Para reasignar una variable exterior: global x o nonlocal x.
    • Closures con enlace tardío: [lambda: i for i in range(3)] devuelve tres funciones que dan 2. Solución: lambda i=i: i.
    • *args recoge posicionales en una tupla; **kwargs, nombrados en un dict. Parámetros solo por nombre tras *: def f(a, *, verbose=False).
Iteradores y generadores: un generador produce valores bajo demanda con yield; memoria O(1) aunque genere millones.
def leer_lineas(ruta):
    with open(ruta, encoding="utf-8") as f:
        for linea in f:
            yield linea.rstrip()
Decoradores: funciones que envuelven a otras para añadir comportamiento (como las anotaciones con proxy de Spring, pero explícitas).
import functools, time

def cronometro(func):
    @functools.wraps(func)                 # conserva nombre y docstring
    def envoltura(*args, **kwargs):
        inicio = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            print(f"{func.__name__}: {time.perf_counter() - inicio:.3f}s")
    return envoltura
8.4 Excepciones y context managers
try:
    datos = cargar(ruta)
except FileNotFoundError:
    datos = {}
except (ValueError, KeyError) as e:
    raise ConfigError("Configuración inválida") from e   # encadena la causa
else:
    print("sin errores")       # solo si no hubo excepción
finally:
    print("siempre")
    • No hay checked exceptions: ninguna excepción obliga a capturarse.
    • No uses except: desnudo: atrapa también KeyboardInterrupt. Como mínimo, except Exception.
    • Estilo EAFP (“es más fácil pedir perdón que permiso”): intentar y capturar, en vez de comprobar antes.
    • with es el equivalente a try-with-resources. Un context manager implementa __enter__ y __exit__, o se crea con @contextlib.contextmanager.
8.5 Clases y POO
from dataclasses import dataclass, field

@dataclass(frozen=True)              # genera __init__, __repr__, __eq__; frozen = inmutable
class Producto:
    nombre: str
    precio: float
    etiquetas: tuple[str, ...] = ()

class Cuenta:
    def __init__(self, titular: str):
        self.titular = titular
        self._saldo = 0.0            # _ = privado por convención

    @property
    def saldo(self) -> float:        # getter sin paréntesis: cuenta.saldo
        return self._saldo

    def __repr__(self):
        return f"Cuenta({self.titular!r})"
    • self es explícito. No hay private real: _x es convención y __x aplica name mangling.
    • @staticmethod (sin self), @classmethod (recibe cls, útil como constructor alternativo).
    • Métodos especiales (dunder): __init__, __repr__, __str__, __eq__, __hash__, __len__, __iter__, __getitem__. Si defines __eq__, define __hash__ (mismo contrato que equals y hashCode).
    • Herencia múltiple permitida; el orden de búsqueda es la MRO (Clase.__mro__, algoritmo C3). super() sigue la MRO, no simplemente el padre.
    • Duck typing: importa que el objeto tenga el método, no su clase. typing.Protocol formaliza esto para el comprobador de tipos (tipado estructural, como TypeScript).
    • abc.ABC y @abstractmethod para clases abstractas.
8.6 Type hints y herramientas
    • Los type hints no se comprueban en ejecución (como TypeScript). Los comprueba mypy o pyright; FastAPI y Pydantic sí los usan en ejecución para validar.
    • Sintaxis moderna: list[int], dict[str, float], int | None, genéricos con def primero[T](xs: list[T]) -> T (3.12+) o TypeVar.
    • Entornos virtuales: aislan dependencias por proyecto (python -m venv .venv).
    • pyproject.toml declara proyecto y dependencias. Gestores: uv (muy rápido, el estándar de facto actual), Poetry, pip + pip-tools.
    • Calidad: Ruff (linter y formateador), mypy, pytest.

asyncio:
import asyncio, httpx

async def descargar(cliente, url):
    r = await cliente.get(url)
    return r.status_code

async def main(urls):
    async with httpx.AsyncClient(timeout=10) as cliente:
        return await asyncio.gather(*(descargar(cliente, u) for u in urls))  # concurrentes

asyncio.run(main(["https://example.com"] * 5))
    • Llamar a una función async def sin await no la ejecuta: devuelve un objeto coroutine (la pregunta 6 de tu diagnóstico).
    • async def no hace asíncrono lo que hay dentro. time.sleep(5) o requests.get() dentro de una corrutina bloquean todo el event loop. Usa asyncio.sleep, httpx, drivers asíncronos, o await asyncio.to_thread(funcion_bloqueante).
    • Concurrencia (asyncio intercala tareas en un hilo) no es paralelismo (procesos en varios núcleos).
8.8 FastAPI
from fastapi import FastAPI, Depends, HTTPException, status
from pydantic import BaseModel, Field, EmailStr

app = FastAPI()

class UsuarioCrear(BaseModel):
    email: EmailStr
    nombre: str = Field(min_length=1, max_length=80)

class UsuarioRespuesta(BaseModel):
    id: int
    email: EmailStr
    nombre: str

def get_db():
    db = SessionLocal()
    try:
        yield db                 # dependencia con limpieza (como try-with-resources)
    finally:
        db.close()

@app.post("/usuarios", response_model=UsuarioRespuesta, status_code=status.HTTP_201_CREATED)
def crear(datos: UsuarioCrear, db: Session = Depends(get_db)):
    if repo.existe_email(db, datos.email):
        raise HTTPException(status.HTTP_409_CONFLICT, "Email ya registrado")
    return repo.crear(db, datos)

@app.get("/usuarios/{usuario_id}", response_model=UsuarioRespuesta)
def obtener(usuario_id: int, db: Session = Depends(get_db)):
    usuario = repo.por_id(db, usuario_id)
    if usuario is None:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "Usuario no encontrado")
    return usuario
    • Los type hints definen parámetros de ruta, query y cuerpo; Pydantic valida y devuelve 422 con detalle si fallan.
    • response_model filtra la salida: separa modelo de entrada, de salida y de base de datos (como los DTO de Spring). Nunca devuelvas el hash de la contraseña.
    • Depends es la inyección de dependencias de FastAPI: sesión de base de datos, usuario autenticado, paginación. Se pueden encadenar y sustituir en tests.
    • def frente a async def en un endpoint: un def se ejecuta en un pool de hilos (seguro con bibliotecas bloqueantes); un async def se ejecuta en el event loop y no debe contener llamadas bloqueantes.
    • Documentación OpenAPI automática en /docs.
    • Persistencia: SQLAlchemy 2 o SQLModel, migraciones con Alembic. Seguridad: OAuth2PasswordBearer + JWT, contraseñas con bcrypt o argon2.
    • Servidor: Uvicorn (ASGI). Tareas pesadas fuera de la petición: Celery, RQ o arq.
    • APIRouter para dividir por funcionalidad, como los controladores.

8.10 asyncio: tareas, límites y timeouts
import asyncio

async def procesar_todos(urls):
    limite = asyncio.Semaphore(10)              # como máximo 10 peticiones a la vez

    async def una(url):
        async with limite:
            async with asyncio.timeout(5):      # Python 3.11+
                return await descargar(url)

    async with asyncio.TaskGroup() as tg:       # Python 3.11+: si una falla, cancela las demás
        tareas = [tg.create_task(una(u)) for u in urls]
    return [t.result() for t in tareas]
    • asyncio.create_task() lanza una corrutina en segundo plano; guarda la referencia o puede ser recolectada.
    • gather(..., return_exceptions=True) recoge errores en lugar de abortar al primero.
    • Lanzar miles de peticiones sin límite satura el servidor remoto y tu pool de conexiones: limita con un Semaphore.

Ciclo de vida (abrir y cerrar recursos compartidos):
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.http = httpx.AsyncClient()   # arranque
    yield
    await app.state.http.aclose()          # cierre

app = FastAPI(lifespan=lifespan)
Middleware y extras: CORSMiddleware para orígenes permitidos; @app.exception_handler(MiExcepcion) para gestión global de errores (como @RestControllerAdvice); BackgroundTasks para trabajo ligero tras responder (emails); para trabajo pesado, una cola.
SQLAlchemy 2 y transacciones
from sqlalchemy import select

def pedidos_pagados(session):
    stmt = (select(Pedido)
            .where(Pedido.estado == "pagado")
            .order_by(Pedido.fecha.desc())
            .limit(20))
    return session.scalars(stmt).all()

def transferir(session, origen_id, destino_id, importe):
    with session.begin():                   # commit al salir; rollback si hay excepción
        origen = session.get(Cuenta, origen_id, with_for_update=True)
        destino = session.get(Cuenta, destino_id, with_for_update=True)
        origen.saldo -= importe
        destino.saldo += importe

    • Con FastAPI asíncrono se usa AsyncSession y un driver asíncrono (asyncpg).
    • Migraciones con Alembic (alembic revision --autogenerate, alembic upgrade head).
Despliegue: Uvicorn con varios workers (uvicorn app.main:app --workers 4) o Gunicorn con workers de Uvicorn, detrás de un proxy inverso (Nginx o el balanceador de la plataforma), empaquetado en Docker y configurado por variables de entorno. Cada worker es un proceso: el estado en memoria no se comparte entre ellos.

Parte 9 — PHP y Laravel
PHP moderno (8.x) es un lenguaje con tipos, enums y clases sólidas; las entrevistas preguntan por comparaciones, arrays y referencias. En Laravel, el foco está en el ciclo de una petición, el service container y Eloquent (sobre todo el N+1).
9.0 Cimientos: PHP y Laravel desde cero
Qué es PHP y cómo funciona
PHP es un lenguaje pensado para la web que se ejecuta en el servidor. Cuando un navegador pide una página, el servidor ejecuta el código PHP, que genera HTML (o JSON) y lo envía. El navegador nunca ve el código PHP, solo el resultado. Una parte enorme de la web funciona con PHP (WordPress, por ejemplo), y Laravel es su framework más popular para aplicaciones modernas.
Modelo clásico de ejecución: cada petición arranca el script desde cero, lo ejecuta y al terminar libera todo. No se guarda nada en memoria entre peticiones; lo que haya que recordar va en base de datos, sesión o caché.
Instalar y ejecutar
    1. Instala PHP 8 (en macOS con Homebrew, en Linux con el gestor de paquetes, en Windows con el instalador oficial o Laravel Herd). Comprueba con php -v.
    2. Ejecutar un script: php hola.php.
    3. Consola interactiva: php -a.
    4. Servidor de desarrollo integrado: php -S localhost:8000 sirve los ficheros de la carpeta actual.
Sintaxis básica
El código PHP va entre <?php y ?> (en ficheros solo de PHP, la etiqueta de cierre se omite).
<?php

9.2 Arrays, objetos y referencias
Aquí PHP es distinto de Java y JavaScript:
    • Los arrays se copian por valor al asignar o pasar a una función (con copy-on-write: la copia real solo ocurre si se modifica). Una función que modifica un array recibido no afecta al original.
    • Los objetos se manejan por handle: se comporta como las referencias de Java. Modificar un objeto recibido sí afecta al original; clone $obj hace una copia superficial.
    • & crea una referencia real: function anadir(array &$lista).
    • Un array de PHP es a la vez lista y mapa ordenado: ['a' => 1, 'b' => 2].
Trampa clásica de foreach por referencia:
$nums = [1, 2, 3];
foreach ($nums as &$n) { $n *= 2; }      // [2, 4, 6]
foreach ($nums as $n) { }                 // $n sigue siendo referencia al último elemento
print_r($nums);                           // [2, 4, 4]  ← el último se sobrescribe
// Solución: unset($n); tras el primer bucle
Funciones de array frecuentes: array_map, array_filter, array_reduce, array_keys, array_column, usort. En Laravel se usan más las Collections (collect($array)->filter()->map()->sum()), equivalentes a los Streams.
9.3 POO, namespaces y Composer

    case Pendiente = 'pendiente';
    case Pagado = 'pagado';
}

final class Pedido {

    • Herencia simple con extends; varias interfaces con implements; clases y métodos abstract y final.
    • Traits: reutilizan métodos copiándolos en varias clases sin herencia (use TieneSlug;). Son reutilización horizontal; no definen un tipo.
    • static:: (enlace estático tardío) frente a self:: (la clase donde está escrito).

    • Estándares PSR: PSR-4 (autoload), PSR-12 (estilo), PSR-7 y PSR-15 (peticiones HTTP y middleware).
    • PHP no mantiene estado entre peticiones en el modelo clásico (PHP-FPM): cada petición arranca desde cero. Laravel Octane cambia esto y obliga a cuidar el estado compartido, como los singletons de Spring.
9.4 Ciclo de una petición en Laravel
    1. public/index.php recibe la petición y carga el autoload de Composer.
    2. Se crea la aplicación (bootstrap/app.php), que es el service container.
    3. Se registran y arrancan los service providers (register() enlaza servicios; boot() los configura).
    4. La petición atraviesa el middleware global y de grupo (sesión, CSRF, autenticación).
    5. El router encuentra la ruta y aplica su middleware.
    6. Se ejecuta el controlador, con sus dependencias inyectadas y la Form Request ya validada.
    7. La respuesta vuelve por el middleware en orden inverso y se envía.

    public function authorize(): bool {
        return $this->user()->can('create', Pedido::class);
    }
    public function rules(): array {
        return [
            'cliente_id' => ['required', 'exists:clientes,id'],
            'lineas' => ['required', 'array', 'min:1'],
            'lineas.*.producto_id' => ['required', 'integer'],

Problema N+1 (la pregunta de Laravel por excelencia):
$pedidos = Pedido::all();                       // 1 consulta
foreach ($pedidos as $p) { echo $p->cliente->nombre; }   // +N consultas, una por pedido

    • Activa Model::preventLazyLoading() en desarrollo para que el N+1 lance una excepción.
    • Asignación masiva insegura: Pedido::create($request->all()) sin $fillable permitiría a un usuario enviar es_admin=1. Usa $fillable y $request->validated().
    • Relaciones: hasOne, hasMany, belongsTo, belongsToMany (tabla pivote), morphMany (polimórficas).
    • Procesar miles de filas: chunk() o lazy() en vez de all().
    • Query Builder (DB::table()) para consultas que no necesitan modelos; ambos usan bindings y evitan la inyección SQL. Cuidado con whereRaw y DB::raw con datos del usuario.
    • Migraciones versionan el esquema (php artisan migrate); cada una con up() y down().
    • Transacciones: DB::transaction(function () { ... }); hace rollback si se lanza una excepción.
9.8 Autenticación y autorización
    • Sanctum: tokens para APIs y autenticación por cookie para SPAs del mismo dominio. Passport: servidor OAuth2 completo.
    • Gates: reglas sueltas (Gate::define('ver-informes', fn ($u) => $u->es_admin)).
    • Policies: reglas agrupadas por modelo (PedidoPolicy::update($user, $pedido)), usadas con $this->authorize('update', $pedido) o can.
    • Contraseñas con Hash::make (bcrypt o argon2). CSRF activo por defecto en rutas web; Blade escapa la salida con {{ }} (protege de XSS); {!! !!} no escapa.
9.9 Colas, eventos y caché
    • Jobs y colas: trabajo lento fuera de la petición (enviar emails, generar PDF). EnviarFactura::dispatch($pedido); drivers Redis, base de datos o SQS; php artisan queue:work. Configura reintentos ($tries), backoff y failed().
    • Los jobs deben ser idempotentes: pueden ejecutarse más de una vez si hay reintentos.
    • Eventos y listeners desacoplan: PedidoPagado dispara enviar email, actualizar stock y notificar, cada uno en su listener (patrón Observer). Un listener puede ir a la cola.
    • Caché: Cache::remember('top-productos', 600, fn () => ...); invalida al cambiar los datos.
    • Scheduler: tareas planificadas definidas en código, con un único cron que ejecuta schedule:run.

9.11 Funciones, closures y cadenas en PHP
function saludar(string $nombre, ?string $titulo = null, string ...$extras): string {

}
saludar(titulo: 'Dr.', nombre: 'Ana');      // argumentos con nombre (PHP 8)

function incrementar(int &$n): void { $n++; } // paso por referencia explícito

$factor = 2;
$doble  = function (int $x) use ($factor) { return $x * $factor; }; // captura por valor
$sumar  = function () use (&$total) { $total++; };                   // captura por referencia

9.12 Excepciones en PHP
    • Jerarquía: Throwable → Exception (errores de aplicación) y Error (errores del motor: TypeError, ValueError, DivisionByZeroError, ArgumentCountError).
    • En PHP 8, dividir entre cero con /, % o intdiv lanza DivisionByZeroError.
    • No hay checked exceptions: nada obliga a capturar.
    • try / catch (A | B $e) / finally, excepciones propias extendiendo Exception o RuntimeException, y encadenamiento con el tercer argumento: new ServicioException('Fallo', 0, $e).
    • En Laravel, el manejador global (bootstrap/app.php, withExceptions) convierte excepciones en respuestas: ModelNotFoundException → 404, ValidationException → 422, AuthorizationException → 403.
9.13 Middleware, configuración y despliegue en Laravel
class ExigirCabeceraApi
{
    public function handle(Request $request, Closure $next): Response
    {
        if (! $request->hasHeader('X-Api-Version')) {
            return response()->json(['error' => 'Falta X-Api-Version'], 400);
        }
        $respuesta = $next($request);                // continúa la cadena
        $respuesta->headers->set('X-Procesado', '1'); // actúa también a la vuelta
        return $respuesta;
    }
}
    • El middleware envuelve la petición como capas de cebolla: el código antes de $next actúa en la ida y el de después, en la vuelta.
    • Configuración: .env para valores por entorno, leídos en config/*.php. Usa env() solo dentro de los ficheros de configuración: con config:cache activado, las llamadas a env() fuera de ellos devuelven null. En el código, config('services.pagos.clave').
    • Despliegue típico: composer install --no-dev --optimize-autoloader, php artisan migrate --force, php artisan optimize (cachea configuración, rutas y vistas), y php artisan queue:restart para que los workers carguen el código nuevo.
    • Los workers de colas deben estar supervisados (Supervisor o Horizon) para reiniciarse si caen.
    • Servidor: PHP-FPM detrás de Nginx, o contenedores Docker. Laravel Octane mantiene la aplicación en memoria entre peticiones para más rendimiento, con el mismo cuidado de estado compartido que un singleton de Spring.

Bases de datos relacionales desde cero
Una base de datos guarda información de forma permanente y permite consultarla rápido aunque haya millones de registros. Las relacionales organizan los datos en tablas, parecidas a hojas de cálculo:

│ id │ nombre │ email         │    │ id │ cliente_id │ total  │ estado  │

│ 1  │ Ana    │ ana@mail.com  │    │ 10 │ 1          │ 45.00  │ pagado  │

    • Cada fila es un registro; cada columna, un dato con un tipo (texto, número, fecha).
    • La clave primaria (id) identifica cada fila de forma única.
    • La clave foránea (cliente_id) apunta a la clave primaria de otra tabla: así se relacionan las tablas. Los pedidos 10 y 11 son de Ana.
Se trabaja con SQL (Structured Query Language). Las cuatro operaciones básicas se conocen como CRUD: crear, leer, actualizar y borrar.
-- Crear una tabla
CREATE TABLE clientes (
  id     SERIAL PRIMARY KEY,           -- autonumérico (PostgreSQL)
  nombre VARCHAR(100) NOT NULL,         -- texto obligatorio
  email  VARCHAR(150) UNIQUE            -- no puede repetirse
);

-- Create: insertar
INSERT INTO clientes (nombre, email) VALUES ('Ana', 'ana@mail.com');

-- Read: consultar
SELECT nombre, email FROM clientes WHERE nombre = 'Ana';
SELECT * FROM pedidos WHERE total > 20 ORDER BY total DESC;

-- Update: modificar (¡sin WHERE cambiaría todas las filas!)
UPDATE pedidos SET estado = 'pagado' WHERE id = 11;

-- Delete: borrar (¡sin WHERE borraría todo!)
DELETE FROM pedidos WHERE id = 12;

-- Unir tablas: el nombre del cliente junto a cada pedido
SELECT c.nombre, p.total
FROM pedidos p
JOIN clientes c ON c.id = p.cliente_id;

-- Agrupar: total gastado por cliente
SELECT cliente_id, SUM(total) AS gastado
FROM pedidos
GROUP BY cliente_id;
Para practicar sin instalar nada: SQLite (un único fichero) o un PostgreSQL en Docker (docker run -e POSTGRES_PASSWORD=secreto -p 5432:5432 postgres) y un cliente como DBeaver. Las secciones 10.2, 10.3 y 10.10 profundizan.
Git desde cero: una máquina del tiempo para tu código
Git guarda la historia de un proyecto: cada commit es una foto del código en un momento, con un mensaje que explica qué cambió. Permite volver atrás, ver quién cambió qué y trabajar en equipo sin pisarse. GitHub y GitLab son webs que alojan repositorios Git en la nube.
Las tres zonas de Git:
    1. Directorio de trabajo: tus ficheros tal como los editas.
    2. Área de preparación (staging): lo que has marcado para el próximo commit con git add.
    3. Repositorio: la historia de commits guardada con git commit.
git init                              # convertir una carpeta en repositorio
git status                            # qué ha cambiado
git add TareaService.java             # preparar un fichero (git add . = todos)
git commit -m "feat: crear servicio de tareas"   # guardar la foto
git log --oneline                     # ver la historia

git switch -c feature/filtros         # crear una rama y cambiarse a ella
# ... trabajar y hacer commits en la rama ...
git switch main                       # volver a la rama principal

Docker desde cero: la aplicación en una caja
El clásico problema: “en mi ordenador funciona”. El servidor tiene otra versión de Java, otra configuración o le falta una biblioteca. Docker empaqueta la aplicación junto con todo lo que necesita (sistema base, Java, dependencias, configuración) en una imagen. Esa imagen se ejecuta igual en cualquier máquina con Docker, como un contenedor de transporte que encaja en cualquier barco o camión.
    • Imagen: la plantilla, de solo lectura (como una clase).
    • Contenedor: una imagen en ejecución (como un objeto). De una imagen puedes lanzar muchos contenedores.
    • Dockerfile: la receta para construir la imagen.
docker run hello-world                   # descargar y ejecutar una imagen de prueba
docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=secreto postgres:16   # una base de datos en segundos
docker ps                                # contenedores en ejecución
docker build -t tareas-api .             # construir una imagen desde el Dockerfile de la carpeta
docker run -p 8080:8080 tareas-api       # ejecutarla: el puerto 8080 del contenedor en el 8080 del equipo
docker logs <id> / docker stop <id>      # ver logs / parar
Docker Compose levanta varios contenedores a la vez (API + base de datos + Redis) descritos en un fichero compose.yaml, con un solo docker compose up. El Dockerfile completo de una aplicación Spring está en 10.8.
CI/CD desde cero
Cada vez que alguien sube código, conviene comprobar automáticamente que compila y que los tests pasan, en lugar de confiar en que cada persona lo haya hecho en su ordenador.
    • CI (integración continua): un servidor (por ejemplo, GitHub Actions) descarga el código en cada push o pull request, compila, ejecuta los tests y avisa si algo falla.
    • CD (entrega o despliegue continuo): si todo pasa, se construye el artefacto (el .jar o la imagen Docker) y se despliega automáticamente a un entorno de pruebas o a producción.
El resultado: los errores se detectan minutos después de cometerlos, no semanas después en producción. Un ejemplo real de pipeline está en 10.17.
Seguridad web desde cero
Todo lo que llega de fuera (formularios, URLs, cabeceras, ficheros) puede venir de alguien con malas intenciones. Tres ideas base:
    1. Nunca confíes en el cliente: valida y autoriza siempre en el servidor. Que un botón esté oculto en el frontend no impide que alguien llame a la API directamente con curl.
    2. Separa datos de código: los ataques más comunes (inyección SQL, XSS) consisten en colar código donde el programa esperaba datos. Por eso se usan consultas parametrizadas y se escapa el HTML.
    3. Autenticación ≠ autorización: autenticar es comprobar quién eres (usuario y contraseña, token); autorizar es decidir qué puedes hacer (un usuario normal no puede borrar pedidos ajenos).
Las contraseñas nunca se guardan tal cual: se guarda un hash, una huella irreversible. Al iniciar sesión se calcula el hash de lo que escribe el usuario y se compara. Los detalles, en 10.4.

10.2 SQL
Orden lógico de ejecución (no el de escritura): FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. Por eso WHERE no puede usar alias del SELECT ni funciones de agregación; HAVING sí filtra agregados.
-- Clientes con más de 3 pedidos pagados en 2026, ordenados por gasto
SELECT c.id, c.nombre, COUNT(p.id) AS num_pedidos, SUM(p.total) AS gasto
FROM clientes c
JOIN pedidos p ON p.cliente_id = c.id
WHERE p.estado = 'pagado' AND p.fecha >= DATE '2026-01-01'
GROUP BY c.id, c.nombre
HAVING COUNT(p.id) > 3
ORDER BY gasto DESC
LIMIT 10;

    • UNION elimina duplicados; UNION ALL no (más rápido).
10.3 Bases de datos: índices, transacciones y diseño
Índices (B-tree por defecto): aceleran búsquedas, joins y ordenaciones a cambio de espacio y escrituras más lentas.
    • Índice compuesto (apellido, nombre): sirve para filtrar por apellido o por ambos, no solo por nombre (regla del prefijo izquierdo).
    • No se usa el índice si aplicas una función a la columna (WHERE YEAR(fecha) = 2026) o con LIKE '%texto'. Reescribe como rango: fecha >= '2026-01-01' AND fecha < '2027-01-01'.
    • Indexa las claves foráneas que usas en joins.
    • EXPLAIN (o EXPLAIN ANALYZE) muestra el plan: busca escaneos completos (Seq Scan, ALL) en tablas grandes.
ACID: Atomicidad (todo o nada), Consistencia (respeta restricciones), Aislamiento (transacciones concurrentes no se pisan), Durabilidad (lo confirmado persiste).

10.5 Git
    • merge une ramas conservando la historia y crea un commit de fusión; rebase reescribe tus commits encima de otra rama y deja una historia lineal. Nunca hagas rebase de ramas compartidas ya publicadas.
    • reset mueve la rama y puede descartar commits (local); revert crea un commit que deshace otro (seguro en ramas compartidas).
    • git pull = fetch + merge (o rebase con --rebase).
    • Otros: stash, cherry-pick, rebase -i para limpiar commits antes de una PR, bisect para encontrar el commit que introdujo un fallo, reflog para recuperar commits “perdidos”.
    • Conflictos: Git marca <<<<<<<, =======, >>>>>>>; resuelves, haces add y continúas el merge o rebase.
    • Flujos: trunk-based (ramas cortas, integración continua a main, feature flags) es el más usado; GitFlow para releases versionadas.
    • Pull requests pequeñas, con descripción, tests y revisión. Commits con mensajes claros (Conventional Commits: feat:, fix:, refactor:).
10.6 Testing: estrategia
Pirámide de tests: muchos unitarios (rápidos, aislados), menos de integración, pocos E2E (lentos, frágiles). Tests de contrato (Pact, Spring Cloud Contract) verifican que productor y consumidor de una API coinciden sin desplegar ambos.
    • Un buen test es rápido, determinista (sin dependencias de hora, orden o red), independiente y comprueba comportamiento.
    • TDD: rojo (test que falla) → verde (código mínimo) → refactor.
    • Tests inestables (flaky) se arreglan o se eliminan: erosionan la confianza en toda la suite.
    • Tu proyecto TaskHub con 983 pruebas en CI es material de entrevista: prepara cómo lo organizaste y qué tipo de pruebas son.
10.7 CI/CD
    • Integración continua: cada push compila, ejecuta tests y análisis estático. Entrega continua: el artefacto siempre está listo para desplegar. Despliegue continuo: se despliega automáticamente.
    • Etapas típicas: checkout → instalar dependencias (con caché) → lint → tests unitarios → build → tests de integración → análisis de seguridad → imagen Docker → despliegue a staging → tests de humo → producción.
    • Quality gates: la PR no se fusiona si fallan tests, cobertura mínima o análisis (SonarQube).
    • Artefacto inmutable: se construye una vez y el mismo se promociona entre entornos; solo cambia la configuración.
    • Estrategias de despliegue: rolling (sustitución gradual), blue-green (dos entornos y cambio instantáneo con vuelta atrás inmediata), canary (un porcentaje pequeño de usuarios primero).
    • Herramientas: GitHub Actions, GitLab CI, Jenkins.
10.8 Docker
    • Imagen: plantilla inmutable por capas. Contenedor: instancia en ejecución de una imagen. Comparte el kernel del host: más ligero que una máquina virtual.
    • Cada instrucción del Dockerfile crea una capa cacheada: copia primero los ficheros de dependencias y después el código para aprovechar la caché.
# Etapa de build
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw dependency:go-offline        # capa cacheada mientras no cambie el pom
COPY src src
RUN ./mvnw package -DskipTests

# Etapa final: solo el JRE y el JAR
FROM eclipse-temurin:21-jre

    • Volúmenes: datos persistentes (el contenedor es efímero). Redes: en Compose, los servicios se resuelven por nombre (db:5432).
    • docker compose up levanta aplicación, base de datos y Redis en local con un compose.yaml.
    • No metas secretos en la imagen; usa .dockerignore.
    • Kubernetes orquesta contenedores en producción: pods, deployments, services, probes de liveness y readiness.
10.9 Arquitectura y sistemas
    • Monolito modular: un despliegue con módulos bien separados. Es el punto de partida recomendado.
    • Microservicios: despliegue y escalado independientes por servicio, a cambio de complejidad distribuida (red, consistencia, observabilidad). Solo compensan con equipos y dominios grandes.
    • Clean / Hexagonal Architecture: el dominio en el centro sin depender de frameworks; la infraestructura (base de datos, HTTP) se conecta mediante puertos (interfaces) y adaptadores. Es DIP aplicado a toda la aplicación.
    • DDD básico: lenguaje ubicuo, entidades, value objects, agregados y bounded contexts.
    • Caché: cache-aside (leer de caché; si falla, de base de datos y guardar). Problemas: invalidación y datos obsoletos. Define siempre un TTL.
    • Colas y mensajería (RabbitMQ, Kafka): desacoplan y absorben picos. La entrega suele ser “al menos una vez”: los consumidores deben ser idempotentes. Patrón outbox para publicar eventos de forma consistente con la base de datos.
    • Escalado: vertical (máquina mayor) u horizontal (más instancias detrás de un balanceador; exige servicios sin estado).
    • Resiliencia: timeouts, reintentos con backoff exponencial, circuit breaker (Resilience4j), rate limiting.
    • Teorema CAP: ante una partición de red, un sistema distribuido elige entre consistencia y disponibilidad.
    • Observabilidad: logs estructurados, métricas (latencia, tasa de errores, tráfico, saturación) y trazas distribuidas.
    • Depuración: reproducir, aislar (bisección), formular una hipótesis, comprobar con datos (logs, depurador, EXPLAIN), corregir y añadir un test de regresión.
10.10 SQL avanzado: subconsultas, CTE y paginación
-- Subconsulta correlacionada: se evalúa por cada fila de la consulta exterior
SELECT p.*
FROM pedidos p
WHERE p.total > (SELECT AVG(p2.total) FROM pedidos p2 WHERE p2.cliente_id = p.cliente_id);

-- EXISTS: se detiene en la primera coincidencia; seguro con NULL
SELECT c.* FROM clientes c
WHERE EXISTS (SELECT 1 FROM pedidos p WHERE p.cliente_id = c.id AND p.estado = 'pagado');

-- Último pedido de cada cliente con CTE + función ventana
WITH ordenados AS (
  SELECT p.*, ROW_NUMBER() OVER (PARTITION BY cliente_id ORDER BY fecha DESC) AS rn
  FROM pedidos p
)
SELECT * FROM ordenados WHERE rn = 1;

-- CTE recursiva: jerarquía de categorías o empleados
WITH RECURSIVE arbol AS (
  SELECT id, nombre, padre_id FROM categorias WHERE padre_id IS NULL
  UNION ALL
  SELECT c.id, c.nombre, c.padre_id FROM categorias c JOIN arbol a ON c.padre_id = a.id
)
SELECT * FROM arbol;

10.11 Bloqueos y deadlocks en base de datos
    • Las escrituras bloquean filas hasta el commit; otra transacción que quiera modificar la misma fila espera.
    • Deadlock: la transacción A bloquea la fila 1 y espera la 2; la B bloquea la 2 y espera la 1. El motor lo detecta y aborta una de ellas con un error.
    • Prevención: acceder a las filas siempre en el mismo orden (por ejemplo, por id ascendente), transacciones cortas, índices adecuados para no bloquear de más, y reintentar la transacción abortada.
    • SELECT ... FOR UPDATE bloquea filas leídas para modificarlas después; FOR UPDATE SKIP LOCKED permite que varios workers tomen tareas distintas de una tabla-cola.
10.12 MongoDB y modelado documental
    • Guarda documentos JSON (BSON) agrupados en colecciones, sin esquema fijo obligatorio.
    • Embeber cuando los datos se leen juntos y su tamaño está acotado (las líneas de un pedido dentro del pedido). Referenciar cuando crecen sin límite o se comparten (los pedidos de un cliente, no dentro del cliente).
    • Límite de 16 MB por documento.
    • Diseña según las consultas que harás, no según la normalización. Los joins ($lookup) existen pero son la excepción.
    • Admite índices, transacciones multidocumento y un pipeline de agregación ($match, $group, $sort, $project).
10.13 Redes y comunicación
    • Cliente-servidor: el cliente inicia la petición; el servidor responde. HTTP no mantiene estado entre peticiones: el estado viaja en cookies, tokens o la URL.
    • HTTP/1.1 (una petición a la vez por conexión), HTTP/2 (multiplexa muchas peticiones en una conexión TCP), HTTP/3 (sobre QUIC/UDP, menos penalización por pérdida de paquetes).
    • Sesión en servidor (cookie con id; el estado vive en el servidor o en Redis; fácil de revocar) frente a token (JWT autocontenido; no requiere almacenamiento compartido; difícil de revocar antes de que expire).
    • Timeouts y reintentos: toda llamada a otro servicio necesita timeout de conexión y de lectura. Reintenta solo operaciones idempotentes, con backoff exponencial y algo de aleatoriedad (jitter) para no saturar al servicio cuando se recupera.
    • Tiempo real: polling (preguntar cada N segundos), Server-Sent Events (el servidor envía, una sola dirección, sobre HTTP) y WebSockets (canal bidireccional persistente: chats, colaboración).
10.14 Seguridad: amenazas y pruebas
    • Modelado de amenazas con STRIDE: Suplantación (Spoofing), Manipulación (Tampering), Repudio, Divulgación de información, Denegación de servicio y Elevación de privilegios. Para cada componente pregunta qué podría salir mal en cada categoría y qué lo mitiga.
    • Auditoría: registra quién hizo qué y cuándo en acciones sensibles (cambios de permisos, borrados), en logs que el propio usuario no pueda alterar.
    • Pruebas de seguridad: SAST (análisis estático del código), DAST (ataques contra la aplicación en marcha, como OWASP ZAP), SCA (dependencias vulnerables) y detección de secretos en el repositorio. Encajan como etapas del pipeline de CI.
    • Rotación de secretos: claves y contraseñas con caducidad, y posibilidad de cambiarlas sin redesplegar.
10.15 Calidad del diseño y refactorización
    • Cohesión: cuánto se relacionan las responsabilidades dentro de un módulo. Alta cohesión = la clase hace una cosa.
    • Acoplamiento: cuánto depende un módulo de los detalles de otro. Bajo acoplamiento = puedes cambiar uno sin romper el otro.
    • Objetivo: alta cohesión y bajo acoplamiento. SOLID, la inyección de dependencias y la arquitectura hexagonal son medios para conseguirlo.
    • Refactorización segura: primero tests que fijen el comportamiento actual (tests de caracterización), después cambios pequeños con los tests en verde tras cada paso, y commits frecuentes para poder volver atrás.
    • Tests flaky: suelen venir de dependencias de hora, orden de ejecución, datos compartidos o esperas con sleep. Se arreglan controlando el reloj, aislando datos y esperando condiciones en lugar de tiempos.

          name: app-jar
          path: target/*.jar
Conceptos: workflow (fichero), job (máquina), step (comando o acción), secrets (credenciales cifradas, nunca en el YAML), matrix (probar varias versiones a la vez) y environments con aprobación manual para producción. Las versiones de las acciones (@v4) cambian; usa las actuales.
Rollback: volver a desplegar el artefacto o la imagen anterior, que sigue existiendo porque son inmutables y están etiquetados por versión. La parte difícil es la base de datos: las migraciones deben ser compatibles hacia atrás (patrón expand / contract: primero añadir la columna nueva, desplegar código que use ambas y solo después borrar la antigua).
10.18 Calidad de las aserciones
    • Comprueba valores concretos, no solo que algo no sea null: assertNotNull(pedido) deja pasar casi cualquier bug.
    • Un comportamiento por test, con un nombre que lo describa; si falla, el nombre ya dice qué se ha roto.
    • Mira el test fallar al menos una vez antes de darlo por bueno: un test que nunca puede fallar no protege nada.
    • Comprueba resultados observables (valor devuelto, estado guardado, respuesta HTTP) antes que llamadas internas con verify.
    • AssertJ hace las aserciones más legibles: assertThat(lista).extracting(Pedido::estado).containsOnly(PAGADO).
    • Los tests de mutación (PIT) cambian tu código a propósito y miden cuántos de esos cambios detectan tus tests: es una medida mejor que la cobertura.

Qué se espera de un perfil junior
No se espera que lo sepas todo. Se espera:
    • Fundamentos sólidos de un lenguaje (en tu caso, Java) y saber explicarlos.
    • Saber usar de forma razonable las tecnologías de la oferta.
    • Escribir código limpio y probado, aunque sea sencillo.
    • Razonar en voz alta cuando no sabes algo, en lugar de quedarte en blanco o inventar.

Cómo leer una oferta de empleo
Separa los requisitos en tres grupos y prepara cada uno de forma distinta:
    1. Imprescindibles (“experiencia con Java y Spring Boot”): repasa a fondo las partes correspondientes de estos apuntes y prepara ejemplos de tus proyectos.
    2. Deseables (“se valorará Docker o Angular”): conocer lo básico y saber explicar qué son.
    3. Desconocidos (una herramienta que no has usado): busca qué es, para qué sirve y con qué se compara de lo que sí conoces. Decir “no lo he usado, pero entiendo que es como X que sí uso” es una buena respuesta.
No te descartes por no cumplir el cien por cien: muchas ofertas describen al candidato ideal, no al mínimo.

    2. Lee la sección de cimientos (x.0) de cada una si no las dominas, y después las secciones concretas.
    3. Responde en voz alta las preguntas de entrevista de esas partes, sin mirar.
    4. Prepara el guion de tus proyectos (11.5 bis).
    5. Haz al menos un simulacro con tiempo (11.7) la semana anterior.

11.2 Respuesta oral en cuatro pasos
Para cualquier pregunta conceptual (“¿qué es X?”), responde en menos de un minuto con esta estructura:
    1. Definición en una frase precisa.
    2. Mecanismo: cómo funciona por dentro.
    3. Ejemplo concreto, mejor si es de tus proyectos.
    4. Trade-off o error típico: cuándo no usarlo o qué suele fallar.
Ejemplo con @Transactional: “Delimita una transacción en un método de servicio: commit si termina bien y rollback si escapa una excepción unchecked. Si no sabes algo, dilo y razona en voz alta: “No lo he usado, pero por cómo funciona X, esperaría que…”. Es mejor que inventar.
11.3 Diseño de sistemas (nivel junior)
Para “diseña un acortador de URLs” o “una API de reservas”:
    1. Requisitos funcionales y no funcionales (usuarios, peticiones por segundo, latencia).
    2. Entidades y modelo de datos.
    3. Endpoints de la API.
    4. Arquitectura básica: cliente, balanceador, servicio, base de datos, caché.
    5. Cuellos de botella y cómo escalar (índices, caché, réplicas de lectura, colas).
    6. Trade-offs que asumes.
A nivel junior no se espera Kafka ni sharding: se espera un diseño razonable y que sepas justificar cada pieza.
11.4 Preguntas de comportamiento: método STAR
Situación, Tarea, Acción (lo que hiciste tú, no el equipo), Resultado (con un dato si es posible). Prepara cinco historias reutilizables:
    • ☐ Un bug difícil que resolviste y cómo lo depuraste.
    • ☐ Una decisión técnica que tomaste y sus alternativas.
    • ☐ Un conflicto o desacuerdo con un compañero.
    • ☐ Algo que aprendiste rápido por necesidad.
    • ☐ Un error tuyo y qué cambiaste después.
